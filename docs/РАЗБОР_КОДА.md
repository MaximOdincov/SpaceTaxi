# Статья 1. Архитектура проекта: как игра собирается из деталей

**Файлы статьи:** весь `Assets/Scripts`, обе сцены, префабы.

## 1.1. Что это за игра

Space Taxi — 2D-игра про космическое такси на Unity 6 (версия редактора `6000.6.0f1`, папка `ProjectSettings/ProjectVersion.txt`). Игрок летает между планетами физически «честно» — под действием гравитации, тормозит двигателями, садится на планеты и возит пассажиров. Рендер — URP (Universal Render Pipeline, видно по `Assets/Settings/UniversalRP.asset` и `Renderer2D.asset`), хотя на логику игры это почти не влияет.

Ключевая идея архитектуры: **весь игровой мир описывается данными** (ScriptableObject `LevelAsset`), **из данных собирается кодом в рантайме** (`WorldBuilder`), и **весь UI строится кодом из этих же данных** (карта, миникарта, радар). Ничего не «нарисовано руками» дважды — один источник истины.

**Вопрос на защите: «Почему код разложен именно по таким папкам?»**
Ответ: папки = namespace'ы = слои ответственности. `Physics` не знает про UI, `UI` читает состояние `Physics`, `World` хранит данные и умеет строить мир из данных, `Core` — связка всего. Это классическое послойное разделение (слои данных → симуляции → представления). Скрипты для редактора вынесены в `Assets/Editor` — Unity компилирует эту папку в отдельную сборку, которая **не включается в билд игры**.

## 1.3. Assembly Definition — что это и зачем

В `Assets/Scripts/` лежит файл `SpaceTaxi.Gameplay.asmdef`:

```json
{
    "name": "SpaceTaxi.Gameplay",
    "rootNamespace": "SpaceTaxi",
    "references": [
        "Unity.InputSystem",
        "Unity.TextMeshPro"
    ],
    "autoReferenced": true
}
```

**Ликбез.** По умолчанию весь код Unity сваливается в одну сборку `Assembly-CSharp`. Файл `.asmdef` говорит: «код из этой папки — отдельная библиотека `SpaceTaxi.Gameplay`, и она явно объявляет, какие пакеты использует». Плюсы: (1) компиляция быстрее — правка одного скрипта не перекомпилирует весь проект; (2) зависимости явные: если бы мы захотели обратиться из gameplay-кода к какому-то редакторскому API, компилятор сразу бы запретил; (3) невозможно случайно создать циклическую зависимость. `autoReferenced: true` означает, что другие сборки (включая `Assembly-CSharp-Editor`, куда компилируется `Assets/Editor`) видят нашу — поэтому редакторские инструменты свободно используют классы игры.

Именно поэтому в YAML-файлах сцен и ассетов у скриптов видно строку вроде
`m_EditorClassIdentifier: SpaceTaxi.Gameplay::SpaceTaxi.Core.GameSession` — Unity хранит «сборка::полное имя класса».

## 1.4. Две сцены и что в них лежит

Сцены перечислены в `ProjectSettings/EditorBuildSettings.asset`: сначала `MainMenu`, потом `GameScene`. Загрузка — по имени (см. статью 12).

**MainMenu.unity** содержит: объекты интерфейса меню, компоненты `SceneFlowButtons` (кнопки «Новая игра»/«Продолжить»), `SceneMusic` (включает музыку меню), инстанс префаба `SettingsUI`.

**GameScene.unity** — «пустая сцена с оживалом»: сама по себе она почти не содержит геймплея. В ней стоят:

- **`GameSession`** — мозг сцены (какие ассеты подключены — см. ниже);
- **Main Camera** — на неё в рантайме добавятся `CameraFollow` и `StarfieldParallax`;
- **HUD** (скрипт `HudBinder`) — скорость, корпус, топливо;
- **Minimap** (`MinimapBinder`) — радар слева внизу;
- **MapScreen/Backing** (`MapScreenBinder` + `MapScreenController`) — экран карты по клавише M;
- **PauseScreen** (`PauseScreenController`) — пауза по ESC;
- инстанс префаба **OnboardComputer** (`OnboardComputerPanel` + `OnboardBinder`) — бортовой компьютер по TAB;
- инстанс префаба **SettingsUI** (`SettingsScreenController` + `SettingsBinder`) — окно настроек (открывается и из меню, и из паузы);
- **Toast** (`ToastNotifier`) — всплывающие сообщения;
- **AudioManager** + **SceneMusic** — звук.

А вот **планет, звёзд и корабля в сцене нет** — их создаёт код при старте. Это осознанное решение: уровень — это данные (`LevelAsset`), мир строится из данных, поэтому один и тот же `GameScene` подходит для любого уровня.

## 1.5. GameSession — точка входа. Что происходит при старте GameScene

Файл: `Assets/Scripts/Core/GameSession.cs` (43 строки — весь):

```csharp
public class GameSession : MonoBehaviour
{
    [SerializeField] private LevelAsset level;             // AlphaMap01.asset
    [SerializeField] private PhysicsConfig physicsConfig;  // PhysicsConfig_Default.asset
    [SerializeField] private InputActionAsset input;       // GameInput.inputactions
    [SerializeField] private PassengerCatalog passengerCatalog;

    [SerializeField] private Planet planetPrefab;          // Planet.prefab
    [SerializeField] private Ship shipPrefab;              // Ship.prefab

    public Ship Ship { get; private set; }
    public OrderService Orders { get; private set; }
    public LevelAsset Level => level;
    public PhysicsConfig Config => physicsConfig;

    private void Start()
    {
        var builder = new WorldBuilder(level, physicsConfig, input, planetPrefab, shipPrefab);
        builder.Build(out Ship ship, out _);
        Ship = ship;

        var follow = Camera.main.gameObject.AddComponent<CameraFollow>();
        follow.SetTarget(Ship);

        // Параллакс-фон на ту же камеру — ощущение полёта между планетами.
        var camGo = Camera.main.gameObject;
        if (camGo.GetComponent<World.StarfieldParallax>() == null)
            camGo.AddComponent<World.StarfieldParallax>();

        Orders = gameObject.AddComponent<OrderService>();
        Orders.Init(level, passengerCatalog, Ship);
    }
}
```

Разбор по строкам:

1. Поля `[SerializeField] private` — **золотой стандарт Unity**: поле приватное (инкапсуляция в C#), но видно в инспекторе благодаря `SerializeField`. Альтернатива — `public`, но тогда поле можно менять откуда угодно из кода, что расслабляет архитектуру. В инспекторе сцены к этому объекту подключены: `level = AlphaMap01`, `physicsConfig = PhysicsConfig_Default`, `input = GameInput`, `passengerCatalog = PassengerCatalog`, оба префаба (это видно в YAML сцены по GUID'ам ассетов).
2. `WorldBuilder` — обычный C#-класс (не MonoBehaviour!). Ему отдают данные, он создаёт все планеты и корабль. Почему не MonoBehaviour: строителю не нужны Update/коллайдеры, он — одноразовая функция. Подробно — статья 7.
3. `Camera.main` — статическое свойство Unity, ищет камеру с тегом `MainCamera` (кэшируется). `AddComponent<CameraFollow>()` — добавляем скрипт слежения на камеру в рантайме, потому что камера в сцене одна и настроена руками (фон, z-позиция), а поведение удобнее вешать кодом.
4. `gameObject.AddComponent<OrderService>()` — сервис заказов тоже добавляется кодом на этот же объект. Порядок важен: сначала мир (иначе заказам не на что ссылаться), потом заказы.

**Порядок инициализации сцены целиком** (важно для защиты, Unity-ликбез):

```
Awake()  всех объектов      — «проснись»: найти компоненты, ничего не искать снаружи
OnEnable()                  — подписки на события
Start()  всех объектов      — «все проснулись, можно знакомиться»: GameSession строит мир
   → WorldBuilder.Build()   — Instantiate префабов (их Awake/OnEnable выполняются сразу)
   → Instantiate корабля    — его Awake тоже сразу
первый Update/FixedUpdate   — игра пошла
```

Практически все скрипты проекта следуют этому правилу: в `Awake` — `GetComponent`/`FindAnyObjectByType` «по соседству», тяжёлый поиск мира — лениво, при первом `Update` (например, `OnboardBinder` ждёт `GameSession` в каждом кадре, пока тот не построит мир — см. статью 10).

**Почему ленивое связывание?** Потому, что `GameSession.Start()` создаёт корабль *после* того, как UI-объекты уже проснулись. UI не может найти корабль в своём `Awake` — его ещё нет. Паттерн «каждый кадр проверяю `if (!bound) { ищу; if (нашёл) подписываюсь; }» — простое и надёжное решение без синглтонов (кроме аудио, там синглтон оправдан — статья 14).

## 1.6. Жизненный цикл кадра: какие скрипты в каких фазах

Это карта всей физики и UI проекта. В течение одного кадра Unity вызывает методы в строгом порядке:

| Фаза | Кто в проекте здесь | Зачем |
|---|---|---|
| **FixedUpdate** (0.02 с, до 50 Гц, не каждый кадр) | `ShipController`, `HullSystem` | вся физика движения и урона от жара |
| физический шаг PhysX2D | — | интеграция позиций, столкновения → `OnCollisionEnter2D` у `LandingSystem` |
| **Update** (каждый кадр) | `ShipController` (взлёт), `TrajectoryPredictor`, `CameraFollow` (нет — см. ниже), `OrderService`, `HudBinder`, `OnboardBinder`, `MapScreenBinder`, `MinimapBinder`, `ToastNotifier`, `StarfieldParallax` (нет) | ввод, UI, логика не связанная с физикой |
| **LateUpdate** (после всех Update) | `CameraFollow`, `StarfieldParallax`, `MapScreenController` (сброс флага ESC) | камера в конце — все уже сдвинулись; фон ещё позже (`[DefaultExecutionOrder(50)]`) |
| отрисовка | — | рендер |

Разница `Update`/`FixedUpdate` — самый частый вопрос. `Update` вызывается раз в кадр (частота = FPS, плавающая), `FixedUpdate` — раз в фиксированный промежуток времени `Time.fixedDeltaTime` (по умолчанию 0.02 с = 50 раз в секунду). Физику считают в `FixedUpdate`, потому что она должна быть детерминированной и одинаковой на любом железе: не важно, 30 у вас FPS или 300, гравитация проинтегрируется одинаковыми шагами.

`Time.deltaTime` — «сколько времени прошло с прошлого кадра» (в Update — кадр, в FixedUpdate — фиксированный шаг). `Time.fixedDeltaTime` — явный фиксированный шаг. `Time.unscaledDeltaTime` — то же, но **не масштабируется паузой** (`Time.timeScale = 0` замораживает `deltaTime`, но не `unscaledDeltaTime`) — на этом построены все UI-анимации, которые должны жить на паузе.

## 1.7. Как связаны части: общая схема потока данных

```
LevelAsset (данные уровня)                        PhysicsConfig (константы)
        │                                              │
        └──────────────┬───────────────────────────────┘
                       ▼
                 GameSession.Start()
                       │
        ┌──────────────┼───────────────────┐
        ▼              ▼                   ▼
   WorldBuilder   CameraFollow +      OrderService
   строит мир     StarfieldParallax   (заказы, слушает
        │         на камеру            посадки и гибель)
        ▼
  Планеты/Звёзды (CelestialBody) + Ship (+ShipController,
  LandingSystem, HullSystem, TrajectoryPredictor, эффекты)
        │
        │ события (C# event Action): FuelChanged, HpChanged,
        │ Died, ShipLost, Respawned, ShipLanded, StationServiced
        ▼
  UI: HudBinder, OnboardBinder, ToastNotifier, карты — только ЧИТАЮТ
  состояние и подписаны на события. UI ничего не знает про физику.
```

Главный принцип: **данные → симуляция → представление**, связь вниз вверх — через **события C#** (`event Action`), вверх вниз — прямые вызовы методов. UI никогда не пишет в физику (единственные «кнопки действия»: `orders.CancelActive()`, `hull.Abandon()`, `landing.Takeoff()` — но это вызовы API симуляции, а не правка её полей).

## 1.8. Префабы: какие и зачем

**Ликбез.** Префаб — сериализованный «шаблон» объекта с компонентами. `Instantiate` создаёт копию, `PrefabUtility.SaveAsPrefabAsset` сохраняет объект как префаб. Экземпляр помнит связь с шаблоном (в YAML это `m_CorrespondingSourceObject` с GUID'ом префаба — поэтому в тексте сцены GUID префаба встречается десятки раз: по одному на каждый сериализованный компонент инстанса).

- **Ship.prefab**: Rigidbody2D (масса 1, `gravityScale: 0`, Continuous-коллизии) + Ship, ShipController, LandingSystem, HullSystem, TrajectoryPredictor, ShipAudio, HeatAudio. `EngineEffects` и `SpeedTrail` в префаб не положили — их WorldBuilder добавляет при создании, если нет (см. статью 7).
- **Planet.prefab**: SpriteRenderer + CircleCollider2D + `Planet`. Радиус коллайдера пересчитывается в `CelestialBody.Init` под фактический размер планеты.
- **OnboardComputer.prefab / SettingsUI.prefab** — готовые куски интерфейса, собранные однажды кодом и сериализованные в префаб (как — статья 10).
- **OfferCard.prefab / ActiveOrder.prefab** — карточки заказов: `OnboardBinder` инстанцирует их и заполняет данные по именам дочерних узлов.

## Вопросы, которые могут задать

**— Почему планеты не расставлены в сцене вручную?**
Уровень — ассет с данными. Ручная расстановка в сцене = дублирование информации: карту, миникарту и валидацию уровня пришлось бы рисовать/проверять отдельно. У нас одна таблица `LevelAsset.Bodies`, из неё строится и мир, и карта, и редактор уровней работает с ней же.

**— Что такое ScriptableObject и почему конфиги — это ассеты?**
ScriptableObject — сериализуемый класс, живущий как файл-ассет (.asset, внутри — YAML). В отличие от MonoBehaviour он не привязан к объекту сцены. Идеален для конфигурации: значения видны и правятся в инспекторе, переживают перезапуск, можно сделать несколько вариантов (`PhysicsConfig_Default`, а мог бы быть `PhysicsConfig_Hardcore`) и поменять баланс без правки кода.

**— Чем `Start` отличается от `Awake`?**
`Awake` — «объект создан», `Start` — «все объекты созданы, первый кадр ещё не был». Поэтому ссылки на свои компоненты берут в `Awake`, а обращение к другим объектам сцены — в `Start` или позже. Ещё нюанс: `Instantiate` вызывает `Awake`/`OnEnable` нового объекта немедленно, а `Start` — только в начале следующего кадра — из-за этого WorldBuilder настраивает корабль вручную после инстанцирования, а не в его `Start`.

**— Где точка входа в игру?**
Билд открывает первую сцену из Build Settings — `MainMenu`. Игровая логика стартует в `GameSession.Start()` игровой сцены.

# Статья 2. Физика I — гравитация: формулы и гравитационные кольца

**Файлы статьи:** `Assets/Scripts/Physics/GravityField.cs`, `Assets/Scripts/Physics/PhysicsConfig.cs`, `Assets/Scripts/World/CelestialBody.cs` (частично).

## 2.1. Физическая модель в двух словах

Настоящая ньютоновская гравитация для двух тел: **F = G·m₁·m₂/r²**, ускорение тела — **a = μ/r²**, где **μ = G·M** — гравитационный параметр центрального тела (для Земли ≈ 3.986·10¹⁴ м³/с²). В игре та же идея, но «масса» тела закодирована через его радиус и множитель:

```csharp
// Файл: Assets/Scripts/Physics/PhysicsConfig.cs
// Гравитационный параметр тела (масса уже внутри).
public float GravParamOf(CelestialBody body)
{
    return GravityParamK * body.Radius * body.MassMultiplier;
}
```

То есть **μ = K · r · m**, где `K = GravityParamK = 52000` (константа баланса), `r` — радиус планеты в юнитах, `m` — `MassMultiplier` (у планет 1, у звёзд 4.5, задаётся в `LevelAsset`). Формально это подмена реальной массы произведением «размер × плотность», зато большие тела автоматически тяжелее, и балансировать силу можно одним числом K в конфиге.

Все значения лежат в ассете `ScriptableObjects/PhysicsConfig_Default.asset`:

```yaml
GravityParamK: 52000        # гравитационный параметр: g = K * r * масса
GravityAccelClamp: 240      # предел ускорения от одного тела
```

**Посчитаем руками** (любимый вопрос преподавателей): планета Кромка из TestLevel01, r = 30, m = 1:
- μ = 52000 · 30 · 1 = **1 560 000**
- на дистанции d = 100 от центра: a = μ/d² = 1.56·10⁶ / 10⁴ = **156 ед/с²**
- на d = 50: a = 624 → но сработает кламп → **240 ед/с²**

## 2.2. GravityField — сумма притяжений всех тел

Файл: `Assets/Scripts/Physics/GravityField.cs` (40 строк). Это «поле», которое знает все тела и умеет отвечать на вопрос «какое ускорение в точке X?»:

```csharp
public class GravityField : MonoBehaviour
{
    private readonly List<CelestialBody> bodies = new List<CelestialBody>();

    public IReadOnlyList<CelestialBody> Bodies => bodies;

    public void Register(CelestialBody body)   { /* добавляет, если нет */ }
    public void Unregister(CelestialBody body) { /* удаляет */ }

    public Vector2 GetAccelerationAt(Vector2 position, PhysicsConfig config)
    {
        Vector2 accel = Vector2.zero;
        foreach (CelestialBody body in bodies)
        {
            Vector2 delta = (Vector2)body.transform.position - position;
            float d2 = delta.sqrMagnitude;
            if (d2 < 0.0001f)
                continue;                                  // защита от деления на ноль
            float d = Mathf.Sqrt(d2);
            float a = Mathf.Min(config.GravParamOf(body) / d2, config.GravityAccelClamp);
            accel += delta / d * a;                        // единичный вектор × величина
        }
        return accel;
    }
}
```

По-настоящему важны четыре детали:

1. **Принцип суперпозиции.** Ускорения от всех тел складываются векторно (`accel += ...`). В системе из 18 тел (AlphaMap01) корабль одновременно притягивается ко всем — поэтому возможны «гравитационные колодцы» между планетами и необычные траектории.
2. **`delta.sqrMagnitude` вместо `delta.magnitude`.** Квадрат длины не требует извлечения корня (это `x²+y²`), корень извлекается один раз и только после проверки `d2 < 0.0001`. Микро-оптимизация, но показательная: `sqrMagnitude` быстрее `magnitude`, и сравнивать квадрат с квадратом — стандартная практика в геймдеве.
3. **Кламп ускорения** `Mathf.Min(a, 240)`. Без него у самой поверхности планеты (d → r, а μ/d² растёт как 1/d²) ускорение взлетало бы до тысяч единиц — корабль «приклеивался» бы к планете со сверхзвуковым ударом. Кламп срезает экстремумы вблизи, сохраняя далёкую динамику честной.
4. **Тела регистрируются сами.** Каждый `CelestialBody` в `OnEnable`/`OnDisable` регистрируется в поле (`FindAnyObjectByType<GravityField>()`). Это паттерн «реестр»: поле не ищет никого, элементы приходят и уходят сами. При старте WorldBuilder сначала создаёт `GravityField`, затем планеты — и они подписываются в момент активации.

**Почему гравитация не через Rigidbody2D?** У PhysX2D есть только постоянное глобальное поле `(0, -9.81)·gravityScale` — направленное притяжение к N движущимся центрам движок не умеет. Поэтому у корабля `Body.gravityScale = 0` (выключаем встроенную гравитацию, см. `Ship.Init`), а свою мы прибавляем к скорости вручную каждый физический шаг.

## 2.3. Где гравитация применяется — явный Эйлер

Файл: `Assets/Scripts/Physics/ShipController.cs`, метод `FixedUpdate` (полный разбор — статья 3). Здесь только физическая суть:

```csharp
Vector2 velocity = ship.Body.linearVelocity;   // текущая скорость тела
Vector2 pos = ship.transform.position;
float dt = Time.fixedDeltaTime;

// Гравитация от всех тел.
if (gravity != null)
    velocity += gravity.GetAccelerationAt(pos, config) * dt;
...
ship.Body.linearVelocity = velocity;
```

Это **явный метод Эйлера**: `v[n+1] = v[n] + a(x[n])·dt`. Скорость обновляем сами, а позицию по скорости двигает сам физический движок (Box2D внутри Unity) на том же шаге. Метод Эйлера накапливает ошибку O(dt) и не сохраняет энергию (орбиты со временем «дышат»), но при dt = 1/50 с и клампе ускорения погрешность незаметна, зато код тривиален и быстр. Альтернативы (Рунге-Кутта, симплектический интегратор, Verlet) точнее, но здесь не нужны — игра аркадная, а не симулятор KSP.

**Ликбез `linearVelocity`.** В Unity 6 свойство `Rigidbody2D.velocity` переименовали в `linearVelocity` (в рамках наведения порядка в API: «линейная» скорость против `angularVelocity`). В старых туториалах — `velocity`, у нас — `linearVelocity`, это одно и то же.

## 2.4. Две «космические» формулы в конфиге

```csharp
// Файл: Assets/Scripts/Physics/PhysicsConfig.cs
// Круговая скорость на дистанции d.
public static float CircularVelocity(float g, float d) => Mathf.Sqrt(g / d);

// Убегающая скорость на дистанции d.
public static float EscapeVelocity(float g, float d) => Mathf.Sqrt(2f * g / d);
```

Это настоящие формулы орбитальной механики: первая космическая **v₁ = √(μ/d)** — скорость круговой орбиты радиуса d; вторая космическая **v₂ = √(2μ/d)** — скорость, с которой тело покидает притягивающий центр навсегда. В игре параметр `g` — это наш `GravParamOf(body)`. Используются в «качели» (следующий пункт). `CircularVelocity` сейчас в коде не вызывается — это заготовка под будущие орбитальные механики.

Пример: та же Кромка (μ = 1.56·10⁶), дистанция d = 100:
- v₁ = √(1.56·10⁶/100) = √15600 ≈ **125 ед/с** — с такой скоростью вокруг неё можно «крутиться»
- v₂ = √2 · v₁ ≈ **176.8 ед/с** — быстрее — улетел навсегда

## 2.5. Кольцо захвата и «качель» (гравитационная праща)

У каждого тела два концентрических кольца (радиусы — свойства `CelestialBody`):

```csharp
// Файл: Assets/Scripts/World/CelestialBody.cs
// Посадочное кольцо: у самой поверхности — включает посадочный режим.
public float LandingRing =>
    landingRingOverride > 0f ? landingRingOverride
                             : Radius + (config != null ? config.LandingRingOffset : 90f);

// Кольцо захвата: большое — зона «качели».
public float CaptureRing =>
    captureRingOverride > 0f ? captureRingOverride
        : Radius * (config != null ? config.CaptureRingK : 3.3f)
                + (config != null ? config.CaptureRingBase : 30f);
```

Для Кромки (r=30): посадочное кольцо = 30+90 = **120**, кольцо захвата = 30·3.3+30 = **129**. Оба радиуса можно переопределить per-planeta в данных уровня (`LandingRingRadius`/`CaptureRingRadius`, 0 = считать по формуле) — гибкость для особых планет.

Логика «качели» — в `ShipController.FixedUpdate`:

```csharp
foreach (CelestialBody body in gravity.Bodies)
{
    float d = Vector2.Distance(body.transform.position, pos);
    float ring = body.CaptureRing;
    bool wasInside = insideRing.Contains(body);
    if (d < ring)
    {
        // впервые вошли в кольцо СЛИШКОМ быстро (быстрее убегающей)?
        if (!wasInside && v > PhysicsConfig.EscapeVelocity(config.GravParamOf(body), d))
        {
            velocity *= config.GravityBoost;   // 1.15 — праща подкидывает скорость
            v = velocity.magnitude;
        }
        insideRing.Add(body);
    }
    else if (wasInside)
    {
        insideRing.Remove(body);
    }
    ...
}
```

Читается так: если корабль **впервые** входит в кольцо захвата со скоростью выше второй космической (гравитация его уже не удержит — пролетит мимо), игра умножает скорость на `GravityBoost = 1.15` — «эффект гравитационной пращи», как у Вояджеров у Юпитера. Дизайнский смысл: у планеты всего два исхода — либо ты в её власти (медленнее убегающей — она тебя закрутит), либо она тебя «швыряет» дальше. Флаг `insideRing` (HashSet) нужен, чтобы буст сработал **один раз на входе**, а не каждый шаг, пока летишь внутри кольца.

Это геймплейная условность, не физика: настоящая праща отнимает/даёт скорость плавно по всей траектории. Здесь — мгновенный «пинок» ×1.15 на границе, зато игрок явно чувствует границу.

## 2.6. Сколько это стоит по производительности

`GetAccelerationAt` — O(N тел) и вызывается из: физики корабля (1 раз/шаг), прогноза траектории (до 360 раз/шаг симуляции, но симуляция — 1 раз/кадр, см. статью 6), жара (перебор только звёзд). Для 18 тел это сотни дешёвых операций — копейки. Если бы тел были тысячи, пришлось бы строить пространственные сетки (grid) или учитывать только ближайшие тела.

## Вопросы, которые могут задать

**— Почему a = μ/d², а не полная формула с G и массами?**
μ = G·M уже объединяет константу и массу. В игре G «съеден» коэффициентом K=52000, а масса выражена через r·m. Физика та же, размерность подобрана под юниты Unity (1 юнит ≈ условный метр).

**— Что будет ровно в центре планеты?**
`d2 < 0.0001 → continue` — деления на ноль нет, тело просто пропускается. Практически туда не попасть — сработает коллизия раньше.

**— Зачем кламп 240 ед/с²?**
Без него у поверхности большой планеты ускорение достигало бы μ/r² = 52000·72/72² ≈ 722 ед/с² для Гавани (r=72) — мгновенный разгон до сотен ед/с за пару шагов, посадка стала бы неуправляемой. Кламп ограничивает «дно» гравитационной ямы.

**— Почему регистрация тел в OnEnable/OnDisable, а не в Start?**
`OnEnable`/`OnDisable` симметричны и вызываются при каждом включении/выключении объекта (в отличие от пары Awake/Start, которые — один раз). Если тело когда-нибудь будут динамически спавнить/удалять — реестр всегда корректен.

**— Почему формулы v₁ и v₂ — static?**
Они не зависят от экземпляра конфига — чистая математика от двух аргументов. static-метод = функция на уровне класса, вызывается `PhysicsConfig.EscapeVelocity(...)` без объекта.

# Статья 3. Физика II — управление кораблём: тяга, тормоз, стрейф

**Файлы статьи:** `Assets/Scripts/Physics/ShipController.cs` (главный файл, 283 строки), `Assets/Settings/GameInput.inputactions`, `Assets/Scripts/Physics/Ship.cs`.

## 3.1. Сначала ввод: как устроена Input System

Проект использует **новую Input System** (пакет `Unity.InputSystem`, он в references нашего asmdef). Описание управления — не в коде, а в ассете `Assets/Settings/GameInput.inputactions` (JSON):

```
Map "Ship":
  Action "Thrust" (Button)   ← W, ↑, Space
  Action "Brake"  (Button)   ← S, ↓
  Action "Strafe" (Value/Axis) ← композит "WASD" (1DAxis): A = -1, D = +1
```

**Ликбез.** Иерархия Input System: **Asset → Map → Action → Binding**. `Map` — группа действий (у нас одна, «Ship»), `Action` — смысл («тяга»), `Binding` — конкретная клавиша. Одна кнопка может иметь несколько биндингов (у Thrust их три: W, стрелка, пробел). У действия есть тип: `Button` (нажато/нет) или `Value` (непрерывная величина, наш Strafe — ось от −1 до 1, собранная из A/D **композитом 1DAxis**).

Как это читается в коде (`ShipController`):

```csharp
private void BindActions()
{
    InputActionMap map = input != null ? input.FindActionMap("Ship") : null;
    if (map == null)
        return;
    thrustAction = map.FindAction("Thrust");
    brakeAction  = map.FindAction("Brake");
    strafeAction = map.FindAction("Strafe");
    map.Enable();
}
```

Три способа опроса действия, все три в проекте есть:

| Вызов | Что возвращает | Где используется |
|---|---|---|
| `action.IsPressed()` | зажата ли прямо сейчас | тяга/тормоз в FixedUpdate |
| `action.ReadValue<float>()` | величина оси (−1..+1) | стрейф |
| `action.WasPressedThisFrame()` | нажата ли в ЭТОМ кадре (фронт) | взлёт в Update |

`map.Enable()/Disable()` в `OnEnable`/`OnDisable` — обязательно: не включённая карта действий не производит значений. Один и тот же ассет передаётся и `ShipController`, и `ShipAudio` — ввод один, слушателей двое.

**Почему не старый `Input.GetKeyDown`?** Input System даёт: разделение «смысл/клавиша» (переназначение управления = правка ассета), честную работу с осью (у Strafe значение −1..1, а не две отдельные клавиши), потокобезопасную обработку событий. Старый Input Manager — глобальный опрос состояния, без слоёв абстракции.

## 3.2. Модель управления: скорость как вектор, корабль как точка

Дизайн-решение игры: **управление не «вверх-вниз-влево-вправо», а вдоль вектора скорости** — как в реальной космической навигации:

- **W / тяга** — ускориться **туда, куда летишь**;
- **S / тормоз (ретро)** — замедлиться (двигатели дуют вперёд по движению);
- **A/D / стрейф** — сместить вектор вбок (кривая траектория).

Все ускорения применяются к вектору скорости, направление носа — чисто визуальное (см. 3.6). Это резко отличает игру от «машинки в космосе» и создаёт всю глубину: чтобы повернуть, нужно не «повернуть руль», а боковым ускорением довернуть вектор скорости.

## 3.3. FixedUpdate по шагам

Скелет метода (сокращённо; полный порядок важен — сохранён):

```csharp
private void FixedUpdate()
{
    config = ship != null ? ship.Config : null;
    if (config == null) return;

    if (ship.State != ShipState.Flying)   // стоим на планете / респавнимся
    { ...сброс индикации...; return; }

    Vector2 velocity = ship.Body.linearVelocity;
    Vector2 pos = ship.transform.position;
    float dt = Time.fixedDeltaTime;

    // 1) ГРАВИТАЦИЯ от всех тел
    velocity += gravity.GetAccelerationAt(pos, config) * dt;

    // 2) КОЛЬЦА: качель + поиск ближайшей планеты
    ... (статья 2, п. 2.5) ...

    // 3) ПОСАДОЧНЫЙ РЕЖИМ: в посадочном кольце двигатели мощнее
    float engMul = 1f;
    if (planet != null && planetDist < planet.LandingRing)
        engMul = config.EngineMultiplier;          // 3.2
    InLandingRing = engMul > 1f;
    EnginePower = engMul;

    // 4) ВВОД
    bool thrustOn = thrustAction != null && thrustAction.IsPressed();
    bool brakeOn  = brakeAction  != null && brakeAction.IsPressed();
    float strafe  = strafeAction != null ? strafeAction.ReadValue<float>() : 0f;

    // 5) ТОПЛИВО: расход на любой двигатель; пустой бак — всё молчит
    if (thrustOn || brakeOn || Mathf.Abs(strafe) > 0f)
        ship.Fuel -= config.FuelDrainPerSecond * dt;    // 5.5/с
    if (ship.Fuel <= 0f) { thrustOn = false; brakeOn = false; strafe = 0f; }
    ThrustOn = thrustOn; BrakeOn = brakeOn; StrafeLevel = strafe;

    // 6) ЛИПКАЯ РЕТРО-ОРИЕНТАЦИЯ (посадочный разворот) — см. статью 5
    ...

    // 7) ДВИЖЕНИЕ — только если скорость выше порога управления
    float v = velocity.magnitude;
    if (v > config.MinControlSpeed)
    {
        Vector2 dir = velocity / v;                     // единичный вектор курса
        if (thrustOn && v < config.MaxV)
            velocity += dir * (config.Thrust * engMul * dt);      // 95·3.2 в кольце
        if (brakeOn)
        {
            float nv = Mathf.Max(0f, v - config.Retro * engMul * dt);  // 80·3.2
            velocity *= nv / v;                          // масштаб вектора до nv
        }
        if (Mathf.Abs(strafe) > 0f)
        {
            Vector2 perp = new Vector2(dir.y, -dir.x);   // перпендикуляр к курсу
            float maxTurn = config.StrafeMaxTurnRate * Mathf.Deg2Rad;
            float strafeAcc = Mathf.Min(config.StrafeAcc, v * maxTurn);
            velocity += perp * (strafe * strafeAcc * engMul * dt);
        }
    }

    ship.Body.linearVelocity = velocity;                // отдаём движку
    UpdateHeading(velocity, v, planet, planetDist);     // поворот носа — статья 5
}
```

Разбор тонких мест:

**Тяга с потолком скорости.** `if (thrustOn && v < MaxV)` — разгон работает только до MaxV = 330 ед/с. Это «мягкий» лимит: не жёсткий кламп `velocity = ClampMagnitude(...)`, а просто прекращение ускорения — гравитация по-прежнему может разогнать и быстрее (например, падение на звезду), праща тоже.

**Торможение — уменьшение модуля.** Сначала считается новая длина `nv = max(0, v − Retro·dt)`, затем вектор масштабируется: `velocity *= nv / v`. Так направление не искажается (можно было бы и `velocity -= dir·Retro·dt`, но при малых v вектор мог бы «перевернуться» через ноль — масштаб до неотрицательной длины безопаснее).

**Стрейф с ограничением кривизны.** Самая красивая формула метода:

```
strafeAcc = min(StrafeAcc, v · StrafeMaxTurnRate[рад/с])
```

Это физика вращения: чтобы вектор скорости длины v поворачивался со скоростью ω, нужно боковое (центростремительное) ускорение **a = v·ω** (следует из a = v²/R и ω = v/R). Ограничение «60°/с поворота вектора» означает: на малой скорости боковое ускорение маленькое (v·ω мало), на большой — растёт, но не выше StrafeAcc = 130 ед/с². Без этого ограничения на медленной скорости корабль крутился бы на месте мгновенно, а на быстрой — не успевал бы поворачивать; с ним траектория всегда имеет ограниченную кривизну и выглядит естественно. `Mathf.Deg2Rad` — константа π/180 для перевода градусов в радианы (формулы вращения требуют радианы).

**Перпендикуляр** `perp = (dir.y, −dir.x)` — поворот единичного вектора на −90°. Проверьте: dir = (1,0) (летим вправо) → perp = (0,−1) (вниз). При dir=(0,1) (летим вверх) → perp=(1,0) (вправо). Стрейф D (+1) всегда толкает курс «вправо от носа».

**Порог MinControlSpeed = 1.** Ниже 1 ед/с управление выключено: у околонулевой скорости вектор курса «шумит» от любого чиха гравитации, и управление вдоль него стало бы источником рывков.

**Посадочный множитель EngineMultiplier = 3.2.** В посадочном кольце (r+90) все двигатели ×3.2: тяга 304, тормоз 256. Зачем: у поверхности нужно быстро гасить падающую скорость, а «космические» 80 ед/с² торможения слишком вялы для этого. При этом множитель честно учитывается и в расходе топлива? — нет! Расход фиксирован 5.5/с независимо от мощности — принятая условность в пользу игрока.

## 3.4. Топливо в свойстве Ship — с событием для HUD

Файл: `Assets/Scripts/Physics/Ship.cs`:

```csharp

{
    get => fuel;
    set
    {
        float clamped = Mathf.Clamp(value, 0f, Config != null ? Config.FuelMax : 100f);
        if (Mathf.Approximately(clamped, fuel))
            return;                 // не изменилось — событие не дёргаем

    }
```

Это паттерн **«свойство с событием изменения»** (аналог INotifyPropertyChanged). Почему не просто `public float Fuel`: HUD должен узнать об изменении. Вариантов два — HUD опрашивает каждый кадр (расточительно для текста/картинки) или подписывается на событие. Событие стреляет только при реальном изменении (`Mathf.Approximately` — сравнение float с допуском, прямое `==` для float ненадёжен из-за погрешности представления).

`ShipState` — еnum из трёх состояний, центральный «рубильник» игры:

```csharp
public enum ShipState { Flying = 0, Landed = 1, Respawning = 2 }
```

`ShipController` в начале FixedUpdate: `if (ship.State != ShipState.Flying) { сбросить индикацию; return; }` — на планете и в респавне физика управления не работает (гравитация, соответственно, тоже не применяется — корабль «заморожен» на поверхности).

## 3.5. Взлёт — во Update, не в FixedUpdate

```csharp
private void Update()
{
    if (ship == null) return;
    if (ship.State == ShipState.Landed && ship.Fuel > 0f
        && thrustAction != null && thrustAction.WasPressedThisFrame())
    {
        landing.Takeoff();
    }
}
```

Взлёт — реакция на **нажатие** (фронт сигнала), а не на удержание, поэтому `WasPressedThisFrame()` и `Update` (кадровая точность: за один физический шаг может быть несколько нажатий-отпусканий, а Update отрабатывает каждое). Что делает `Takeoff()` — статья 5.

## 3.6. Ориентация носа: три режима

Метод `UpdateHeading` поворачивает спрайт корабля (визуал, на физику не влияет). Три целевых угла:

1. **Обычный полёт** — нос по вектору скорости: `target = atan2(v.y, v.x)`.
2. **Ретро-ориентация** (`retroAttitude`, включается тормозом в посадочном кольце — статья 5) — нос **против** скорости (`+180°`): корабль опускается двигателями вперёд, как Falcon 9.
3. **Финальное выравнивание** (около поверхности: дистанция < r+40 и v < 50) — нос строго **от центра планеты** (вертикаль).

Доворот — экспоненциальный с ограничением:

```csharp
float delta = Mathf.DeltaAngle(current, target);
float step = Mathf.Clamp(
    delta * config.HeadingTurnRate * dt,               // «экспонента»: 4·dt от остатка
    -config.HeadingMaxTurnSpeed * dt,                  // но не быстрее 260°/с
    config.HeadingMaxTurnSpeed * dt);
ship.Body.MoveRotation(current + step);
```

- `Mathf.DeltaAngle(a, b)` — **кратчайшая** угловая разница a→b в диапазоне ±180° (сам написать легко ошибиться из-за перехода 359°→0°).
- Произведение `delta * HeadingTurnRate * dt` — это дискретизация экспоненциального приближения: за каждый шаг поворачиваемся на 4/50 долю остатка → быстрый доворот в начале, плавный в конце.
- Кламп ±260°/с спасает у околонулевой скорости: остаток `delta` там скачет на сотни градусов каждый шаг (вектор скорости «шумит»), без клампа нос щёлкал бы как бешеный. Плюс два предохранителя выше по коду: при `v < 30` доворот вообще выключен (`if (!finalApproach && v < 30f) return;`).
- `Rigidbody2D.MoveRotation` вместо `transform.rotation =` — метод «физически корректного» поворота: учитывает интерполяцию тела и не ломает коллизии.

**`spriteNoseAngle`** — поле-компенсация: спрайт корабля нарисован носом вправо (0°), а формула `atan2` тоже даёт 0° для «вправо», поэтому по умолчанию поле 0. Если бы взяли спрайт носом вверх (90°), достаточно указать 90 — и всё продолжает работать. Это простая, но редкая у начинающих развязка «математика курса» и «арт».

## Вопросы, которые могут задать

**— Почему управление в FixedUpdate, а не в Update?**
Управление меняет скорость физического тела. Если менять в Update (частота = FPS), при 144 Гц двигались бы в 2.4 раза быстрее, чем при 60. FixedUpdate нормирует физику по времени.

**— Как называется ваш метод интегрирования?**
Явный Эйлер: v += a·dt. Погрешность O(dt), для аркады достаточно; шаг фиксирован 0.02 с.

**— Что такое композит в Input System?**
Составной биндинг: несколько клавиш собираются в одно значение-ось (1DAxis: A → −1, D → +1). Код читает уже готовое значение `ReadValue<float>()`.

**— Почему у тяги лимит скорости именно «прекратить ускорение», а не жёсткий кламп?**
Жёсткий кламп `v = min(v, MaxV)` обрезал бы и разгоны от гравитации/пращи, ломая физику. Мягкий вариант ограничивает только тягу — «двигателю не хватает мощности», физические разгоны сохраняются.

**— Зачем HashSet insideRing?**
Хранить «в каких кольцах я уже был», чтобы событие входа (буст качели) сработало один раз, на пересечении границы. HashSet — O(1) на Contains/Add, порядок не важен.

## 4.1. Где что лежит

Константы (из `PhysicsConfig_Default.asset`): `FuelMax: 100`, `FuelDrainPerSecond: 5.5`, `HpMax: 100`.

## 4.2. API HullSystem — события вместо опроса


## 4.3. Урон и ремонт

```csharp
public void ApplyDamage(float amount)
{
    if (amount <= 0f || ship == null || ship.Hp <= 0f)
        return;                                  // мёртвых не бьём и пустой урон — тоже
    ship.Hp = Mathf.Clamp(ship.Hp - amount, 0f, ship.Config.HpMax);
    HpChanged?.Invoke();
    if (ship.Hp <= 0f)
        Die();
}

// Полный ремонт (станция): именно через метод — с событием HpChanged,
// иначе HUD не узнает и цифра зависнет на старом значении.
public void RepairAll()
{

    ship.Hp = ship.Config.HpMax;
    HpChanged?.Invoke();
}
```

Обратите внимание на комментарий про `RepairAll` — это типичная ошибка, которую код специально предотвращает: менять `ship.Hp` напрямую нельзя (HUD не узнает), только через методы, которые дёргают событие. Единицы урона в игре: удар при посадке `(v − LandSpeed)·0.9` (статья 5), жар звезды — ниже.

## 4.4. Жар звёзд — линейная зона

Звезда (класс `Star`, статья 7) имеет `HeatRadius` (у Печи в TestLevel01 — 180) и `HeatDamagePerSecond = 30`. Логика — в `HullSystem.FixedUpdate → ApplyHeat`:

```csharp
private void ApplyHeat(float dt)
{
    if (gravity == null) return;
    Vector2 pos = ship.transform.position;
    foreach (CelestialBody body in gravity.Bodies)
    {
        if (!(body is Star star) || star.HeatRadius <= 0f)
            continue;                                  // интересуют только звёзды
        float d = Vector2.Distance(star.transform.position, pos);
        if (d >= star.HeatRadius)
            continue;                                  // снаружи зоны — ничего
        // линейная интерполяция: 0 на краю зоны → 1 у поверхности
        float k = Mathf.Clamp01(1f - (d - star.Radius) / (star.HeatRadius - star.Radius));
        ApplyDamage(k * star.HeatDamagePerSecond * dt);
    }
}
```

Формула `k = 1 − (d − r)/(HeatRadius − r)` — обычная **линейная интерполяция (обратная lerp / обратное нормирование)**: на краю зоны d=HeatRadius → k=0, у поверхности d=r → k=1. Урон в секунду = 30·k, умножается на dt — это «урон как скорость» (30 ед/с у поверхности; за 0.02 с шага — 0.6 ед). Почему в FixedUpdate: урон непрерывный во времени, его надо интегрировать с физическим шагом, иначе при просадке FPS урон «дешевел» бы.

Касание самой звезды — мгновенная смерть (`LandingSystem`: `Hull.ApplyDamage(ship.Hp)`, статья 5), жар — постепенный. Двойная механика опасности: приближение наказуемо, контакт фатален.

## 4.5. Два способа потерять корабль: Die и Abandon

**Die** — HP достиг нуля (взрыв):

```csharp
private void Die()
{
    if (ship.State == ShipState.Respawning) return;    // повторно не умираем
    Died?.Invoke();
    CameraFollow.AddShake(0.85f);                      // гибель — самый сильный толчок
    ship.State = ShipState.Respawning;
    ship.Body.linearVelocity = Vector2.zero;
    StartCoroutine(RespawnAfter(0.6f));                // короткая пауза на взрыв
}
```

**Abandon** — потеря без взрыва: кнопка «ОТКЛЮЧИТЬ КОРАБЛЬ» на бортовом компьютере (появляется при пустом баке) или выход за границу системы:

```csharp
private void Update()
{
    // Потеря связи: корабль покинул систему (граница из данных уровня).
    if (ship == null || ship.State != ShipState.Flying) return;
    float worldRadius = level != null ? level.WorldRadius : 2500f;
    if (ship.transform.position.magnitude > worldRadius)
        Abandon("ПОТЕРЯНА СВЯЗЬ");
}

public void Abandon(string reason)
{
    if (ship == null || ship.State == ShipState.Respawning) return;
    ShipLost?.Invoke(reason);                          // тост покажет причину
    ship.State = ShipState.Respawning;
    ship.Body.linearVelocity = Vector2.zero;
    StartCoroutine(RespawnAfter(0.6f));
}
```

`transform.position.magnitude` — расстояние от центра мира (0,0): граница системы — окружность радиуса `WorldRadius` (2600 в AlphaMap01). Причина передаётся строкой в событии — минимальная, но честная параметризация UI-сообщения.

Разница Die/Abandon важна для подписчиков: `Died` семантически «взрыв», `ShipLost` — «нет сигнала». Оба ведут в один респавн, но тосты разные («КОРАБЛЬ ПОТЕРЯН — ПОТЕРЯНА СВЯЗЬ» vs. тихий респавн после взрыва — на самом деле на Died ToastNotifier тоста не делает, он показывает «Респавн на планете старта» по `Respawned`; провал заказа слушает оба события).

## 4.6. Респавн — корутина

```csharp
private System.Collections.IEnumerator RespawnAfter(float delay)
{
    yield return new WaitForSeconds(delay);            // 0.6 с на «взрыв»

    if (level != null && level.StartPlanetIndex >= 0 && level.StartPlanetIndex < level.Bodies.Count)
    {
        CelestialBodyData start = level.Bodies[level.StartPlanetIndex];
        float rad = level.SpawnAngleDeg * Mathf.Deg2Rad;
        Vector2 dir = new Vector2(Mathf.Cos(rad), Mathf.Sin(rad));
        transform.position = start.Position + dir * (start.Radius + 7f);
        float nose = GetComponent<ShipController>() != null
            ? GetComponent<ShipController>().SpriteNoseAngle : 0f;
        transform.rotation = Quaternion.Euler(0f, 0f, level.SpawnAngleDeg - nose);
    }

    ship.Body.linearVelocity = Vector2.zero;
    ship.Hp = ship.Config.HpMax;
    ship.Fuel = ship.Config.FuelMax;   // бак полный (12_ALPHA_PLAN §3.4)
    ship.LandedOn = ... /* поиск Planet по имени стартовой планеты */;
    ship.State = ShipState.Landed;
    HpChanged?.Invoke();
    Respawned?.Invoke();
}
```

**Ликбез — корутины.** `IEnumerator` + `yield return` — **корутина** Unity: метод приостанавливается на `yield return`, а Unity возобновляет его, когда выполнится условие. `new WaitForSeconds(0.6f)` — «продолжить через 0.6 игровых секунд». Корутина живёт на объекте (`StartCoroutine` на MonoBehaviour) и умирает вместе с ним. Важно: `WaitForSeconds` учитывает `Time.timeScale` — при паузе (timeScale=0) респавн замрёт. Это не баг: в паузе и смерть наступить не может.

Геометрия спавна — та же, что у WorldBuilder (статья 7): позиция = центр планеты + направление под углом `SpawnAngleDeg` × (радиус + 7 юнитов — ровно над поверхностью, 7 ≈ половина длины корабля). Угол 90° — «север» планеты. `Quaternion.Euler(0,0, SpawnAngleDeg − nose)` — поворот на угол минус компенсация спрайта (нос от центра планеты).

Штучка напоследок: `ship.LandedOn` после респавна ищется **по имени** (`LandedPlanet()` сравнивает `planet.name == Bodies[StartPlanetIndex].DisplayName`) — потому что объекты уровня и данные уровня — разные сущности, связаны только именем. Так worldbuilder именует GameObject'ы: `go.name = data.DisplayName`.

## Вопросы, которые могут задать

**— Почему урон от жара в FixedUpdate, а проверка границы в Update?**
Жар — непрерывный физический процесс (интеграл по времени, нужен dt физического шага). Граница — событие «пересёк окружность», точность кадра достаточна.

**— Что будет, если ApplyDamage вызвать дважды в один кадр?**
Сработает дважды — так и задумано (жар каждый физический шаг). Повторная смерть предотвращена стейт-флагом: `if (ship.State == ShipState.Respawning) return;`.

**— Почему Hp — public поле, а Fuel — свойство?**
Историческая эволюция кода: Fuel сделали свойством с событием, Hp оставили полем, но доступ — только через HullSystem-методы, которые дёргают HpChanged. «Правильнее» было бы тоже свойство; текущий вариант — компромисс (в комментах кода это честно отражено).

**— Чем ShipLost отличается от Died по геймплею?**
Оба = респавн. Разница — семантика для UI (причина потери) и для заказов: OrderService подписан на оба и в любом случае проваливает активный заказ.

# Статья 5. Посадка, взлёт и посадочные режимы

**Файлы статьи:** `Assets/Scripts/Physics/LandingSystem.cs` (122 строки), куски `ShipController.cs` (ретро-ориентация), `CelestialBody.cs` (кольца).

## 5.1. Правила посадки

- Мягкое касание (скорость контакта < `LandSpeed = 55` ед/с) — **посадка**.
- Быстрее — **удар**: урон `(v − 55)·0.9` (минимум 5), выжил — считай сел.
- Касание **звезды** — мгновенная гибель, независимо от скорости.
- Посадка на планету со **станцией** (`HasStation`) — бесплатный полный ремонт и заправка.
- Взлёт — W/Space на планете (нужен бак > 0): импульс `TakeoffV = 85` от центра планеты.

`LandSpeed` поднимали 38 → 55 (комментарий в конфиге): «окно мягкой посадки шире, станции обслуживают только мягкую посадку» — балансное решение, задокументированное прямо в ассете.

## 5.2. Точка входа — коллизия

```csharp
private void OnCollisionEnter2D(Collision2D collision)
{
    if (ship == null || ship.Config == null || ship.State != ShipState.Flying)
        return;                                          // стоим/респавн — коллизии игнорируем

    Planet planet = collision.collider.GetComponentInParent<Planet>();
    Star star = collision.collider.GetComponentInParent<Star>();
    float v = collision.relativeVelocity.magnitude;      // скорость ОТНОСИТЕЛЬНО точки контакта

    if (star != null)
    {
        Hull.ApplyDamage(ship.Hp);                       // звезда смертельна
        return;
    }
    if (planet == null)
        return;

    if (v < ship.Config.LandSpeed)
        Land(planet, collision);
    else
        Crash(planet, collision, v);
}
```

**Ликбез — коллизии 2D.** `OnCollisionEnter2D` — физический коллбек (вызывается физическим движком при первом контакте твёрдых тел; есть ещё Stay/Exit). Параметр `Collision2D` содержит: `collider` (тело, о которое ударились), `relativeVelocity` (относительная скорость в точке контакта — для посадки это именно «скорость касания», а не скорость корабля в мире), `contacts[]` (точки и нормали).

`GetComponentInParent<Planet>()` — ищет компонент не на объекте, а у него и вверх по иерархии: коллайдер висит на том же GameObject, что и Planet (префаб плоский), но код устойчив и к дочернему коллайдеру. Проверка через `is`-полиморфизм: и Planet, и Star — наследники CelestialBody.

Почему у планет `CircleCollider2D` (круг): круг — идеальный коллайдер для шарообразной планеты: контакт с окружностью всегда даёт точную нормаль от центра, нет «углов», дешевейшая проверка. Радиус коллайдера подгоняется в `CelestialBody.Init` под фактический размер (статья 7).

## 5.3. Land — «шлёп» и снап на поверхность

```csharp
private void Land(Planet planet, Collision2D collision)
{
    Vector2 normal = collision.contactCount > 0
        ? collision.contacts[0].normal
        : (Vector2)(transform.position - planet.transform.position).normalized;

    // Снап на поверхность, скорость в ноль, нос от центра.
    Vector2 pos = (Vector2)planet.transform.position + normal * (planet.Radius + 7f);
    transform.position = pos;
    ship.Body.linearVelocity = Vector2.zero;
    float nose = GetComponent<ShipController>() != null
        ? GetComponent<ShipController>().SpriteNoseAngle : 0f;
    float angle = Mathf.Atan2(normal.y, normal.x) * Mathf.Rad2Deg;
    transform.rotation = Quaternion.Euler(0f, 0f, angle - nose);

    ship.LandedOn = planet;
    ship.State = ShipState.Landed;
    CameraFollow.AddShake(0.08f);                        // лёгкий «шлёп» касания
    ShipLanded?.Invoke(planet);                          // ← единственная точка взятия/сдачи пассажира

    if (planet.HasStation)                               // станция: бак/корпус полные
    {
        bool healed = ship.Hp < ship.Config.HpMax;
        bool refueled = ship.Fuel < ship.Config.FuelMax;
        Hull.RepairAll();
        ship.Fuel = ship.Config.FuelMax;
        if (healed || refueled)
            StationServiced?.Invoke(planet.DisplayName); // тост «Станция ...: бак и корпус полны»
    }
}
```

Ключевые решения:

1. **Снап (привязка) позиции.** После касания корабль телепортируется на `center + normal·(Radius + 7)` — ровно над поверхностью. Зачем: физический контакт мог случиться в «скользящий» момент, корабль частично утоплен в коллайдер или висит на расстоянии; снап даёт чистую, воспроизводимую стоянку и убивает дребезг (вместе с обнулением скорости и выключением физики управления через `State = Landed`).
2. **Нормаль контакта с фолбэком.** `collision.contacts[0].normal` — нормаль из физдвижка (у контакта круг-круг она всегда направлена от планеты к кораблю). Фолбэк «от центра планеты на корабль» покрывает вырожденный случай контактов=0.
3. **`ShipLanded` — событие-интерфейс для остальных систем.** На него подписан OrderService (взять/сдать пассажира, статья 8). Единственная точка в коде, где происходит «игрок сел на планету» — значит, все правила посадки меняются в одном месте.
4. **Флаги healed/refueled до вызова** — чтобы тост «станция обслужила» не показывался при посадке на уже полном баке и целом корпусе (мелочь, но пользователь сразу бы заметил спам).

## 5.4. Crash — удар с уроном

```csharp
private void Crash(Planet planet, Collision2D collision, float v)
{
    float damage = Mathf.Max(5f, (v - ship.Config.LandSpeed) * 0.9f);
    Hull.ApplyDamage(damage);
    CameraFollow.AddShake(Mathf.Clamp01(damage / 45f) * 0.7f);   // от «бумкнул» до «въехал»
    ...
    if (ship.Hp > 0f)
        Land(planet, collision);                          // выжил — считай сел
}
```

Формула урона линейная по превышению скорости: удар на 100 ед/с → (100−55)·0.9 ≈ 40 урона; на 155 → 90; на ~166+ → смерть. Минимум 5 — любой удар ощутим. Сила тряски камеры пропорциональна урону, с насыщением (Clamp01/45·0.7: при уроне 45+ — максимум тряски для этого события). Смерть обработается внутри `ApplyDamage → Die` (статья 4), и до `Land` дело не дойдёт — «смерть есть смерть» (комментарий в коде).

## 5.5. Takeoff — импульс от центра

```csharp
public void Takeoff()
{
    if (ship == null || ship.State != ShipState.Landed || ship.LandedOn == null)
        return;
    Vector2 dir = ((Vector2)ship.transform.position - (Vector2)ship.LandedOn.transform.position).normalized;
    ship.Body.linearVelocity = dir * ship.Config.TakeoffV;    // 85 ед/с строго вверх
    ship.LandedOn = null;
    ship.State = ShipState.Flying;
    CameraFollow.AddShake(0.25f);                             // толчок старта
}
```

Взлёт задаёт скорость **напрямую** (`linearVelocity = dir·85`), а не силой/импульсом (`AddForce` с импульсом зависел бы от массы). Почему так: надёжность и повторяемость — игрок всегда отрывается с одинаковой скоростью строго по нормали. Это же значение 85 использует редактор уровней для прогноза траектории взлёта (статья 15).

## 5.6. «Липкая» ретро-ориентация — главный трюк посадки

Проблема: при подлёте к планете корабль летит носом вперёд; чтобы тормозить, надо развернуться на 180°. Поворот руками (стрейфом) у поверхности сложен и долог. Решение — автоматический «посадочный разворот» в ShipController:

```csharp
// Липкая посадочная ориентация: тормоз в кольце разворачивает корабль
// двигателями к планете — и держит так до посадки, выхода из кольца
// или тяги (W). Отпускание S больше не разворачивает нос обратно.
private bool retroAttitude;

// В FixedUpdate:
bool finalApproach = InLandingRing && planet != null
    && planetDist < planet.Radius + 40f && v < 50f;
if (retroAttitude)
{
    if (!InLandingRing || thrustOn)          // выход: покинул кольцо ИЛИ дал тягу
        retroAttitude = false;
}
else if (InLandingRing && !finalApproach && brakeOn && ship.Fuel > 0f)
{
    retroAttitude = true;                     // вход: тормоз внутри посадочного кольца
}
```

Слово «липкая» = состояние само не отменяется отпущенной кнопкой. Конечный автомат из трёх визуальных режимов (статья 3, п. 3.6):

```
обычный полёт (нос по скорости)
   │  тормоз (S) внутри посадочного кольца (r+90)
   ▼
ретро-ориентация (нос против скорости, двигателями вперёд)
   │  приблизился к поверхности (< r+40) ИЛИ замедлился (< 50)
   ▼
финальное выравнивание (нос строго вертикально от планеты)
```

Откат к обычному полёту — только выход из кольца или тяга W («уходим на второй круг»). Свойство `LandingRetro` публично торчит наружу: его читают камера (зум 190 — приблизить посадку), прогноз траектории (скрыть пунктир — при ретро он врёт), эффекты (развернуть ретро-сопло), HUD. Единая точка правды о режиме — один флаг.

## 5.7. Посадочное кольцо и EngineMultiplier — сводка чисел

| Параметр | Значение | Где |
|---|---|---|
| Радиус посадочного кольца | r + 90 | `LandingRingOffset` |
| Множитель двигателей в кольце | ×3.2 | `EngineMultiplier` |
| Порог мягкой посадки | 55 ед/с | `LandSpeed` |
| Высота стоянки над центром | r + 7 | константа `ShipOffset` в WorldBuilder и LandingSystem |
| Импульс взлёта | 85 ед/с | `TakeoffV` |
| Финальное выравнивание | дистанция < r+40 и v < 50 | константы в ShipController |

## Вопросы, которые могут задать

**— Почему relativeVelocity, а не velocity корабля?**
Относительная скорость в точке контакта учитывает движение обоих тел. Планеты у нас статичны, так что численно совпадает, но семантически правильно и пережило бы движущиеся станции.

**— Почему вы гасите скорость в ноль, а не оставляете физику?**
Управление «вдоль вектора скорости» у нулевой скорости не определено (статья 3). Стационарная стоянка с ручной ориентацией — предсказуемое состояние, из которого взлёт даёт чистый результат.

**— Что если два корабля столкнутся?**
Оба получат OnCollisionEnter2D, но второй коллайдер — не Planet/Star → `planet == null → return`. Пассажирских кораблей в альфе нет — код просто безопасен.

**— Почему посадка через коллизии, а не проверка дистанции в Update?**
Коллизии считает физический движок с реальными формами и субшагами — контакт не «проскочит» на скорости. Проверка дистанции на 300 ед/с при 60 FPS пропускает 5 юнитов за кадр — можно пролететь сквозь планету.

# Статья 6. Визуальная обратная связь: камера, прогноз траектории, эффекты

**Файлы статьи:** `CameraFollow.cs`, `TrajectoryPredictor.cs`, `EngineEffects.cs`, `SpeedTrail.cs`.

Игра сделана по принципу « juice»: каждое физическое событие имеет зрительное (и звуковое) эхо. Четыре скрипта — четыре канала обратной связи.

## 6.1. CameraFollow: опережение, зум, тряска

Файл: `Assets/Scripts/Physics/CameraFollow.cs` (102 строки). Синглтон (`Instance`) + статический метод `AddShake(power)` — любой код игры трясёт камеру: взлёт 0.25, посадка 0.08, удар ~0.7·урон/45, гибель 0.85.

Три независимых поведения в `LateUpdate`:

**а) Взгляд вперёд (lookahead):**

```csharp
Vector2 velocity = ship.Body != null ? ship.Body.linearVelocity : Vector2.zero;
Vector2 targetOffset = ship.State == ShipState.Flying
    ? Vector2.ClampMagnitude(velocity * LookaheadSeconds, LookaheadMax)   // 0.45с, макс 130
    : Vector2.zero;
lookOffset += (targetOffset - lookOffset) * Mathf.Min(1f, 3f * dt);
```

Смещение цели камеры = «где я буду через 0.45 с», ограничено 130 юнитами. Игрок видит больше пространства **по курсу** — куда летишь, а не откуда. Сглаживание — экспоненциальное: `x += (target − x)·min(1, k·dt)`; множитель `k·dt` делает скорость приближения независимой от FPS (при 144 Гц и `min(1,...)` насыщение — корректно и там).

**б) Позиция и тряска (trauma-модель):**

```csharp
Vector2 target = (Vector2)ship.transform.position + lookOffset;
pos.x += (target.x - pos.x) * Mathf.Min(1f, 3.5f * dt);   // плавное следование
pos.y += (target.y - pos.y) * Mathf.Min(1f, 3.5f * dt);
AnchorPosition = pos;                                     // ← якорь для параллакса (без тряски!)

trauma = Mathf.Max(0f, trauma - ShakeDecay * dt);         // спад линейный
float shake = trauma * trauma;                            // сила = trauma²
float t = Time.time;
Vector2 shakeOffset = new Vector2(
    Mathf.PerlinNoise(noiseSeed, t * 14f) * 2f - 1f,      // гладкий шум вместо Random
    Mathf.PerlinNoise(noiseSeed + 31f, t * 14f) * 2f - 1f)
    * (ShakeAmplitude * shake);                           // 15 юнитов при trauma=1
transform.position = pos + (Vector3)shakeOffset;
transform.rotation = Quaternion.Euler(0f, 0f,
    (Mathf.PerlinNoise(noiseSeed + 77f, t * 14f) * 2f - 1f) * ShakeRotation * shake);
```

Это **классическая модель screen shake** (trauma model, популяризована докладами GDC — «Juice it or Lose It», Squirrel Eiserloh):

- `trauma` — накопитель «стресса» 0..1; `AddShake` прибавляет, каждый кадр линейно спадает (1.6/с);
- амплитуда = **trauma²** — квадратичная кривая: лёгкие толчки почти незаметны, сильные — резки. Квадрат ещё и гарантирует плавный старт/конец (производная в нуле = 0);
- смещение берётся из **шума Перлина**, а не `Random`: Perlin гладко меняется во времени → дрожь «живая», без телепортаций картинки. `PerlinNoise(seed, t·14)` — просто гладкая функция от времени; три разных seed'а (0/+31/+77) для X, Y и поворота;
- к дрожи добавлен и поворот камеры (±2.5°) — вращательная тряска ощущается сильнее трансляционной.

`AnchorPosition` — та же позиция, но **до** тряски. Её читает параллакс фона (статья 13): звёзды не должны дрожать вместе с камерой, иначе дрожь не видна (мир бы дрожал синхронно и целиком).

**в) Зум (ортографический размер):**

```csharp
bool landing = ship.State == ShipState.Landed || controller.LandingRetro;
float vNorm = Mathf.Clamp01(velocity.magnitude / ship.Config.MaxV);    // 0..1
float viewHeight = landing ? LandingViewHeight                          // 190 — посадка
    : Mathf.Lerp(FlightViewHeight, FastViewHeight, vNorm);              // 320 → 470
cam.orthographicSize += (viewHeight * 0.5f - cam.orthographicSize) * Mathf.Min(1f, 3f * dt);
```

**Ликбез.** У ортографической камеры нет «расстояния до объекта»; вместо него `orthographicSize` — половина высоты видимой области в юнитах. Высота 320 = размер 160. Динамика: чем быстрее летишь — тем дальше «отъезжает» камера (эффект скорости), при посадке — наоборот приближается (точность важнее обзора). Переход сглажен той же экспонентой.

Почему `LateUpdate`: камера должна встать **после** того, как все объекты сдвинулись в этом кадре (иначе она отстаёт на кадр — виден «резиновый» корабль). `StarfieldParallax` выполняется ещё позже — `[DefaultExecutionOrder(50)]` (статья 13).

## 6.2. TrajectoryPredictor: пунктир будущего

Файл: `Assets/Scripts/Physics/TrajectoryPredictor.cs` (216 строк). Пульс игры: пунктирная линия показывает, куда тебя **повезёт** гравитация, если ничего не делать. Структура:

**Пул чёрточек.** В `Awake` создаётся 64 GameObject'а со SpriteRenderer (чёрточка — спрайт-капсула из StubSprites, статья 13), все выключены. Переиспользуем циклично — никаких Instantiate/Destroy в кадре (аллокации → GC-паузы → дёрганья).

**Скрытие.** Линия не нужна: не в полёте, в ретро-режиме, скорость < 30 (`sqrMagnitude < 900` — сравнение квадратов, без корня). При околонулевой скорости прогноз не имеет смысла — гравитация крутит вектор как хочет.

**Адаптивный горизонт** — сколько секунд вперёд симулировать:

```csharp
// ~1.2 экрана вперёд: t = расстояние/скорость
float target = Mathf.Clamp(HorizonScreens * refWidth / Mathf.Max(speed, 1f), HorizonMin, HorizonMax);
horizon += (target - horizon) * Mathf.Min(1f, 4f * Time.deltaTime);   // сглаживание 4/с
```

`refWidth` — опорная ширина экрана, посчитанная **один раз** в `Start`: `2·160·aspect` (высота 320 → половина 160 × аспект). Фиксированная, а не живая от зума: зум камеры «дышит» (статья 6.1), линия при живой ширине дёргалась бы. Горизонт 2–4 с: короткий горизонт ещё и уменьшает «хлёст» конца линии — чувствительность к начальным условиям растёт как t² (характеристика хаотических систем; по сути — ляпуновская неустойчивость орбиты).

**Симуляция — тот же явный Эйлер, что и физика:**

```csharp
int steps = Mathf.CeilToInt(horizon / step);        // step = 1/120 (тоньше физики!)
for (int i = 0; i < steps && !contact; i++)
{
    vel += gravity.GetAccelerationAt(pos, config) * step;
    Vector2 next = pos + vel * step;
    float seg = Vector2.Distance(pos, next);
    travelled += seg;

    foreach (CelestialBody body in gravity.Bodies)
        if (Vector2.Distance(body.transform.position, next) < body.Radius + 4f)
        { contact = true; contactPlanet = body is Planet; contactSpeed = vel.magnitude; break; }

    if (travelled >= spacingNow && dashIndex < dashes.Count)
    {
        PlaceDash(dashIndex++, next, vel, total, spacingNow);
        travelled = 0f;
    }
    pos = next;
}
```

Прогноз дублирует формулу гравитации игры (тот же `GetAccelerationAt`) — если физика и прогноз разойдутся, игрок перестанет верить линии. Шаг 1/120 вдвое тоньше физического: линия рисуется редко (1 раз/кадр), можно позволить.

**Расстановка чёрточек по пройденному пути** (не по времени!): `travelled` копит длину пути, чёрточка ставится каждые `spacingNow` юнитов — при ускорении чёрточки реже, при торможении гуще... нет, наоборот: spacing фиксируется по юнитам, поэтому визуально плотность одинакова по пространству, а по времени чёрточки «разрежаются» с ростом скорости — правильное восприятие темпа.

**Цвет = исход.** Если симуляция коснулась **планеты** со скоростью меньше `LandSpeed` — вся линия зелёная («сейчас будешь мягкая посадка»):

```csharp
Color lineColor = contact && contactPlanet && contactSpeed < config.LandSpeed
    ? LineSafe    // зелёный #3CFF8E — тот же, что «безопасная скорость» в HUD
    : dashColor;  // обычный белёсый
```

Красного «опасного» цвета сознательно нет (комментарий в коде): траектория к планете краснела бы почти всегда — пугала бы. Опасность показывают цифра скорости и цвет в посадочном кольце (статья 9). Каждая чёрточка ещё и тускнеет к концу (`endFade`, alpha по индексу).

**Стабилизация направления.** Стартовая точка — от носа корабля (`noseOffset = 6`), начальная скорость — сглаженный вектор курса: вектор скорости на малой скорости шумит, поэтому направление прогноза сглаживается (`smoothDir`, доворот до 720°/с) — линия стоит спокойно, нос может дёргаться.

## 6.3. EngineEffects: выхлоп из четырёх сопел

Файл: `Assets/Scripts/Physics/EngineEffects.cs`. Четыре `ParticleSystem` создаются **кодом** в `Awake` (главный выхлоп из кормы — тёплый, ретро из носа — холодный голубой, два маневровых сверху/снизу). Состояние двигателей контроллер уже вычислил (с учётом пустого бака и режимов) — эффектам остаётся включать/выключать эмиcсию:

```csharp
bool flying = ship.State == ShipState.Flying;
SetEmission(mainJet,      flying && controller.ThrustOn);
SetEmission(retroJet,     flying && controller.BrakeOn);
SetEmission(strafeTop,    flying && controller.StrafeLevel > 0f);
SetEmission(strafeBottom, flying && controller.StrafeLevel < 0f);

// Ретро: при посадочном развороте нос против скорости — сопло разворачиваем
retroJet.transform.localRotation = controller.LandingRetro ? RetroFlipped : RetroForward;

// У поверхности двигатели в 3+ раза мощнее — пламя гуще и крупнее
float power = Mathf.Max(1f, controller.EnginePower);
ApplyPower(mainJet, power);
```

**Ликбез — ParticleSystem кодом.** Настройки системы частиц разбиты на модули (`ps.main`, `ps.emission`, `ps.shape`, `ps.colorOverLifetime`, `ps.sizeOverLifetime`); в коде модуль сначала «открывается» свойством (`var em = ps.emission;`), потом пишется (`em.enabled = ...`) — так устроен API (структуры-обёртки, пишущиеся обратно в систему). Материал — созданный в рантайме `new Material(shader) { mainTexture = ... }` из круглой текстуры-заглушки. Градиент `colorOverLifetime` даёт «остывание» выхлопа (от белого к оранжевому с затуханием альфы), `sizeOverLifetime` — сужение струи.

`TrailRenderer`, добавляемый кодом, включается только выше 65 ед/с; толщина растёт со скоростью (`Lerp(0.5, 2.6, v/MaxV)`). Тонкость — `trail.Clear()` при смене состояния корабля: после телепорта (посадка/респавн) шлейф «тянулся» бы через полкарты от старой позиции к новой.

## Вопросы, которые могут задать

**— Почему Perlin-шум лучше Random для тряски?**
Random каждому кадру даёт независимые значения — картинка «телепортируется» случайно, выглядит как помехи. Perlin гладкий по времени — непрерывное «дрожание». Плюс trauma² даёт правильную нелинейность нарастания.

**— Почему прогноз в Update, а не в FixedUpdate?**
Прогноз — визуализация, физике он не нужен; рендер-кадр достаточно. Вызов `GetAccelerationAt` тут до ~360 раз за кадр (3с × 120), но только когда корабль в полёте и экран не в режиме посадки.

**— Что такое пул объектов и зачем он тут?**
Заранее созданный набор переиспользуемых объектов. Чёрточек 64; в кадре мы лишь двигаем существующие и включаем/выключаем. Альтернатива (Instantiate/Destroy по 64 объекта за кадр) дала бы мусор для сборщика каждый кадр — фризы.

**— Чем LateUpdate лучше Update для камеры?**
Гарантия порядка: все Update (в т.ч. физическое перемещение от прошлого FixedUpdate и ввод) уже выполнены. Иначе камера следовала бы за позицией прошлого кадра — корабль «плавал» бы относительно центра экрана.

## 7.2. CelestialBody → Planet, Star: наследование

```csharp
// Файл: Assets/Scripts/World/CelestialBody.cs
[RequireComponent(typeof(CircleCollider2D))]     // без кругового коллайдера — ошибка инспектора
public class CelestialBody : MonoBehaviour
{
    public string DisplayName = "Body";
    public BodyType Type = BodyType.Planet;
    public float Radius = 50f;
    public float Mass = 1f;
    public bool HasStation { get; private set; }

    public float LandingRing  => ...   // r + 90 или override  (статья 2)
    public float CaptureRing  => ...   // r·3.3 + 30 или override

    public virtual void Init(CelestialBodyData data, Physics.PhysicsConfig physicsConfig)
    {
        DisplayName = data.DisplayName;
        Type = data.Type;  Radius = data.Radius;  Mass = data.MassMultiplier;
        HasStation = data.HasStation;
        spinSpeed = data.Visuals != null ? data.Visuals.SpinSpeed : 0f;
        landingRingOverride = data.LandingRingRadius;
        captureRingOverride = data.CaptureRingRadius;
        transform.position = data.Position;

        // Масштаб спрайта под фактический радиус:
        var renderer = GetComponent<SpriteRenderer>();
        if (renderer != null && renderer.sprite != null)
        {
            float d = Mathf.Max(renderer.sprite.bounds.size.x, renderer.sprite.bounds.size.y);
            if (d > 0.0001f)
            {
                float s = Radius * 2f / d;
                transform.localScale = new Vector3(s, s, 1f);
            }
        }

        // Коллайдер — в ЛОКАЛЬНЫХ единицах: делим на масштаб родителя
        float scale = Mathf.Max(Mathf.Abs(transform.localScale.x), Mathf.Abs(transform.localScale.y), 0.0001f);
        GetComponent<CircleCollider2D>().radius = Radius / scale;
    }

    protected virtual void OnEnable()  { /* Register в GravityField */ }
    protected virtual void OnDisable() { /* Unregister */ }

    private void Update()
    {
        if (!Mathf.Approximately(spinSpeed, 0f))
            transform.Rotate(0f, 0f, spinSpeed * Time.deltaTime);   // декоративное вращение
    }
}

// Файл: Planet.cs — пустой класс!
public class Planet : CelestialBody { }

// Файл: Star.cs
public class Star : CelestialBody
{
    public float HeatRadius = 180f;
    public float HeatDamagePerSecond = 30f;

    public override void Init(CelestialBodyData data, Physics.PhysicsConfig cfg)
    {
        base.Init(data, cfg);
        HeatRadius = data.HeatRadius;
    }

    public bool IsInHeatZone(Vector2 point)
        => Vector2.Distance(point, transform.position) <= HeatRadius;

```

Три объяснения:

1. **Зачем пустой класс Planet?** Тип-маркер. Код по всему проекту спрашивает `body is Planet` / `collision.GetComponentInParent<Planet>()` — «это планета?». Семантика важна: сажаться можно только на Planet, но не на Star. Если бы был один класс, пришлось бы проверять `Type == BodyType.Planet` везде — тип-наследник надёжнее (полиморфизм вместо сравнения enum).
2. **Масштаб спрайта.** Спрайт планеты (например, `planet_stub.png`, PPU 2.56, размер 256×256 → 100 юнитов) надо растянуть ровно на диаметр `2·Radius`. `sprite.bounds.size` — размер спрайта в мировых юнитах при scale=1. Итог: `scale = 2r / d`. Планета любого радиуса из любого спрайта — одна формула.
3. **Коллайдер и scale.** `CircleCollider2D.radius` задаётся в **локальных** координатах и умножается на масштаб трансформа. Чтобы мировой радиус коллайдера равнялся Radius, локальный радиус = `Radius / scale`. Классическая ловушка — отсюда деление.

`[RequireComponent(typeof(CircleCollider2D))]` — атрибут Unity: при добавлении CelestialBody на объект коллайдер добавится автоматически, удалить его нельзя, пока висит скрипт. Страховка от «планета без коллайдера пролетает насквозь».

Детали:

- **Планеты инстанцируются из префаба** (спрайт/материал настраиваются в префабе и переопределяются данными через `ApplyVisuals`), **звёзды — целиком кодом**: для них хватит процедурного круга StubSprites + прозрачного ореола жара. Решение «префаб vs код» здесь прагматичное: планеты — контент (хотим красивые спрайты в инспекторе), звёзды — функциональные объекты.
- **sortingOrder** — порядок отрисовки 2D-спрайтов внутри слоя: −1 (жар позади), 0 (планеты), 1 (звёзды поверх жара, но под кораблём — у корабля 2, чёрточки прогноза 1, выхлоп 3).

```csharp

        controller = go.GetComponent<ShipController>();
        shipAudio = go.GetComponent<ShipAudio>();
    }
    else
    {                                                    // фолбэк: собрать всё кодом
        go = new GameObject("Ship");
        go.SetActive(false);                             // ← ВАЖНО: собираем неактивным
        ...
        var rb = ship.GetComponent<Rigidbody2D>();
        rb.collisionDetectionMode = CollisionDetectionMode2D.Continuous;
        rb.interpolation = RigidbodyInterpolation2D.Interpolate;
    }

    // Позиция старта: над планетой под углом SpawnAngleDeg
    float angleRad = level.SpawnAngleDeg * Mathf.Deg2Rad;
    Vector2 dir = new Vector2(Mathf.Cos(angleRad), Mathf.Sin(angleRad));
    go.transform.position = start.Position + dir * (start.Radius + ShipOffset);   // +7
    go.transform.rotation = Quaternion.Euler(0f, 0f, level.SpawnAngleDeg - nose);

    ship.Init(config);                                   // конфиг, gravityScale=0, бак/корпус
    ship.State = ShipState.Landed;                       // начинаем СТОЯЩИМ на планете
    ship.LandedOn = bodies[level.StartPlanetIndex] as Planet;

    controller.SetInput(input);
    shipAudio.SetInput(input);
    go.GetComponent<HullSystem>().Init(level);           // уровень для респавна

    if (go.GetComponent<EngineEffects>() == null) go.AddComponent<EngineEffects>();
    if (go.GetComponent<SpeedTrail>() == null)    go.AddComponent<SpeedTrail>();

    go.SetActive(true);

```

Три классических приёма в одном методе:

1. **Сборка неактивного объекта** (`SetActive(false)` → добавить компоненты → настроить → `SetActive(true)`). Пока объект неактивен, его `Awake/OnEnable` не вызываются — компоненты не успевают «сработать» с недонастроенным состоянием. Все настройки — потом, одной вспышкой активации.
2. **`AddComponent` с проверкой** (`if (GetComponent<X>() == null) AddComponent<X>()()`) — идемпотентность: не задвоить компоненты, если префаб их уже содержит.
3. **Тот же `as Planet`** — если стартовое тело вдруг звезда, `LandedOn` будет null (безопаснее, чем исключение; редактор уровней отдельно предупреждает о «старте на звезде» — статья 15).

Настройки Rigidbody2D корабля, которые надо уметь назвать: **`collisionDetectionMode = Continuous`** — непрерывная проверка коллизий (дискретная на скорости 330 ед/с может пропустить тонкую стенку — «прострел» насквозь; continuous дороже, но у нас одно быстрое тело); **`interpolation = Interpolate`** — интерполяция позиции между физическими шагами для отрисовки: физика 50 Гц, рендер 60–144 Гц, без интерполяции движение дёргается. Эти же значения зашиты в Ship.prefab.

## Вопросы, которые могут задать

**— Почему WorldBuilder не MonoBehaviour?**
Его роль — одноразовое построение. MonoBehaviour нужен для жизненного цикла (Update и т.п.), который строителю не нужен. Чистый класс проще, тестируемее, не «засоряет» сцену.

**— Что даёт [RequireComponent]?**
Гарантию наличия компонента на этапе редактора: Unity сам добавит его и запретит удалять. Проверка `GetComponent<CircleCollider2D>()` в Init становится безопасной.

**— Как планета находит GravityField без ссылки в инспекторе?**
`FindAnyObjectByType<GravityField>()` в OnEnable. Порядок создания в Build() это обеспечивает: сначала поле, потом тела. Поиск по типу — медленный, но выполняется один раз при старте.

**— Чем звезда отличается от планеты в коде?**
Классом (Star : CelestialBody) с HeatRadius/HeatDamagePerSecond, массой 4.5 и смертельным контактом; планеты имеют станции и посадку. Общее (гравитация, кольца, отрисовка) — в базовом классе: наследование как переиспользование.

**— Где хранятся деньги/прогресс уровня?**
Нигде — мир только геометрия и параметры. Прогресс (доставки/провалы) живёт в OrderService в памяти сессии (статья 8), экономика — заготовка.

## 8.1. Модель данных

```csharp
public enum OrderState
```

**Почему индексы, а не ссылки на планеты?** Уровень — данные (LevelAsset), планеты — объекты сцены. Заказы живут в «координатах данных»: `PickupIndex` — индекс в списке `level.Bodies`. Имя планеты для UI — `PlanetName(index)` (обходной мостик «данные → имя»). Так заказы не зависят от сцены: не бывает «висячей ссылки» на удалённый объект, уровень и заказы согласованы по построению.

Правила альфы (зашиты в код):
- **один активный заказ** (`Accept` отклонит второй: `if (Active != null) return false`);
- **посадка — единственная точка взятия/сдачи** (подписка на `LandingSystem.ShipLanded`);
- провал — только гибель/потеря корабля;
- счётчики `Deliveries`/`Failures` — в памяти сессии.

## 8.2. Поток входящих карточек

```csharp
[Header("Поток карточек")]
public float offerLifetime = 60f;   // сколько живёт карточка
public float spawnMin = 15f;        // новая: минимум через
public float spawnMax = 30f;        //         максимум через
public int maxOffers = 4;           // максимум одновременно
public int initialOffers = 2;       // сразу на старте

private void Update()
{
    // 1) Смертность: просроченные — вон
    int before = offers.Count;
    offers.RemoveAll(o => Time.time >= o.ExpiresAt);
    if (offers.Count != before)
        OffersChanged?.Invoke();

    // 2) Появление новой; while — если кадры «застревали» (пауза, лаг),
    //    догоняем пропущенные тики, а не ждём следующего
    while (Time.time >= nextSpawnAt)
    {
        if (offers.Count < maxOffers)
            AddOffer(catalog);
        nextSpawnAt = Mathf.Max(nextSpawnAt + Random.Range(spawnMin, spawnMax),
                                Time.time + 2f);
    }

    UpdateTargetGlow();
}
```

Хитрость с `while` и `Mathf.Max(..., Time.time + 2f)`: время спавна хранится «следующий тик», а не «таймер до». Если игра стояла на паузе или кадр длился секунду, простой `if` сдвинул бы расписание на весь простой; while-цикл догоняет мгновенно, а нижняя граница +2с не даёт появиться пачке карточек в один кадр. `RemoveAll` с лямбда-предикатом — идиоматичное удаление по условию из List.

`Time.time` — игровое время (стоит при паузе) → на паузе карточки не стареют и не спавнятся. Правильно: пауза честная.

## 8.3. Жизненный цикл заказа — все переходы

```
                Accept(offer)                посадка на планету A        посадка на планету B
  Offered ────────────────────▶ Active ─────────────────────▶ Aboard ─────────────────▶ Delivered
     │ expiry/Decline                │                              │                     ▲
     ▼                               │ Died / ShipLost              │                     │
  (исчезает)                         └──────────────┬───────────────┘                     │
                                                    ▼                                         │
                                                 Failed ◀── CancelActive (с пассажиром —    │
                                                            только стоя на планете) ─────────┘
```

**Accept/Decline/Cancel:**

```csharp
public bool Accept(OrderOffer offer)
{
    if (Active != null || !offers.Contains(offer))
        return false;
    offers.Remove(offer);
    offer.State = OrderState.Active;
    Active = offer;
    OffersChanged?.Invoke();
    ActiveOrderChanged?.Invoke();
    return true;
}

public bool CancelActive()
{
    if (Active == null) return false;
    if (Active.State == OrderState.Aboard)          // с пассажиром:
    {
        Ship ship = FindAnyObjectByType<Ship>();
        if (ship == null || ship.State != ShipState.Landed)
            return false;                           // только стоя на планете (высадить)
    }
    OrderOffer cancelled = Active;
    Active = null;
    OrderCancelled?.Invoke(cancelled);
    ActiveOrderChanged?.Invoke();
    return true;
}
```

Дизайн-логика отмены: без пассажира — отмена в любой момент (ничья ничья), с пассажиром — только на поверхности: «высадить человека нельзя в открытом космосе» — правило из геймдизайн-дока, и оно же защита от злоупотреблений.

**Посадка — единственная точка взятия/сдачи:**

```csharp
private void OnLanded(Planet planet)                      // подписка на LandingSystem.ShipLanded
{
    if (Active == null) return;
    int idx = PlanetIndexByName(planet.DisplayName);
    if (idx < 0) return;

    if (Active.State == OrderState.Active && idx == Active.PickupIndex)
    {
        Active.State = OrderState.Aboard;
        PassengerBoarded?.Invoke(Active);
    }
    else if (Active.State == OrderState.Aboard && idx == Active.DropoffIndex)
    {
        Active.State = OrderState.Delivered;
        Deliveries++;
        OrderOffer done = Active;
        Active = null;
        OrderDelivered?.Invoke(done);
        ActiveOrderChanged?.Invoke();
    }
}
```

Мостик «объект сцены → данные»: `PlanetIndexByName(planet.DisplayName)` ищет планету по имени в `level.Bodies`. Стыковка строк — слабое место (переименовал планету в редакторе — заказы сломались), осознанное упрощение альфы.

**Провал:**

```csharp
    var hull = ship.GetComponent<HullSystem>();
```

`ShipLost += reason => FailActive()` — лямбда-подписка: событие с параметром-причиной подключено к методу без параметров. Сама причина в заказах не нужна (тост покажет её отдельно).

## Вопросы, которые могут задать

**— Почему заказы — MonoBehaviour (AddComponent), а WorldBuilder — нет?**
Заказам нужен Update (время жизни, спавн, подсветка) и события. Строителю — нет. Монобех только там, где нужен жизненный цикл.

**— Как UI узнаёт, что список предложений изменился?**
События `OffersChanged`/`ActiveOrderChanged`; OnboardBinder на них полностью перестраивает зону заказа (статья 10). UI не опрашивает список каждый кадр.

**— Что если игрок принял заказ и просто стоит?**
Ничего не случится: у заказа нет таймера, у пассажира — терпения. Дизайн альфы; таймеры — заготовка на бету.

**— Почему Random с большими буквами и UnityEngine.Random?**
В файле подключён и System (нет), точнее — во избежание конфликта System.Random и UnityEngine.Random код местами пишет `UnityEngine.Random.Range` явно. UnityEngine.Random — статический ГПСЧ Unity с интерфейсом Range(float,float)/Range(int,int) (int-версия — исключающая верхняя граница, float — включающая).

## 9.2. ToastNotifier — очередь сообщений

Тост — плачка сверху («Пассажир на борту: Марк Ветров — „привет!"»). Вся плачка рисуется кодом в Awake (Image + CanvasGroup + TMP-текст с якорями), объект **никогда не деактивируется** — прячется прозрачностью:

```csharp
// Объект НЕ выключаем: у неактивного Update не вызывается, и мы
// никогда не подпишемся на события. Прячем прозрачностью.
group.alpha = 0f;
```

Комментарий — готовый ответ на «почему SetActive(false) нельзя»: подписки на события выполняются в `Update` (лениво), неактивный объект не получает Update → тосты умерли бы после первого скрытия.

**Очередь** — события могут прийти пачкой (доставка → тут же что-то ещё):

```csharp
public void Show(string message, bool emphasized = false)
{
    queue.Enqueue((message, emphasized));    // кортеж — данные без класса
}

private void Update()
{
    if (group.alpha > 0f && Time.unscaledTime >= hideAt)
        group.alpha = 0f;                    // время вышло — растворились
    if (group.alpha <= 0f && queue.Count > 0)
    {
        var next = queue.Dequeue();
        Display(next.message, next.emphasized);
    }
    ...ленивые подписки...
}
```

`Queue<(string, bool)>` — очередь кортежей. Показ 3.5 с, важные (доставка/провал) — 5 с, крупнее и шире. `Time.unscaledTime` — чтобы на паузе тосты доживали своё (пауза их не должна «замораживать» на полэкрана).

**Подписки — карта событий игры в одном методе:**


## 9.3. PauseScreenController — пауза и война за ESC

```csharp
private void Update()
{
    var kb = Keyboard.current;
    if (kb == null) return;
    if (!kb.escapeKey.wasPressedThisFrame) return;
    // ESC занят: карта открыта или только что закрылась этим нажатием
    if (mapController != null && (mapController.IsOpened || mapController.EscJustClosed)) return;
    SetPaused(!paused);
}

private void SetPaused(bool value, bool force = false)
{
    if (!force && value == paused) return;
    paused = value;
    pauseScreen.SetActive(paused);
    onboard.Show(paused);        // пауза с борт.компом; продолжить — панель уходит
    Time.timeScale = paused ? 0f : 1f;      // ← вся пауза — одна строчка
}
```

**Пауза = `Time.timeScale = 0`.** Ликбез: timeScale масштабирует игровое время. При 0: FixedUpdate не вызывается, `Time.deltaTime` = 0, корутины на WaitForSeconds стоят, анимации стоят. Но `Update` вызывается, `Time.unscaledDeltaTime` течёт — на этом и построен UI, живущий на паузе (тосты, панель бортового компьютера, карта). `force: true` в `Start` — инициализация без срабатывания логики переключения.

**Конфликт ESC.** На ESC завязаны: пауза и закрытие карты. Если карта открыта и жмёшь ESC — карта закрывается, но и пауза бы переключилась (двойное действие!). Решение — флаг на MapScreenController:

```csharp
// MapScreenController:
else if (opened && kb.escapeKey.wasPressedThisFrame)
{
    SetOpened(false);
    EscJustClosed = true;             // «ESC только что съеден картой»
}
private void LateUpdate() { EscJustClosed = false; }   // живёт ровно один кадр
```

Классический паттерн «однокадровый флаг»: потребление события одним обработчиком, сброс в LateUpdate. Порядок выполнения Update у разных компонентов не определён — флаг страхует от любого порядка.

**Взаимодействие паузы с картой и настройками** — явные методы-уведомления вместо неявного состояния:

```csharp
public void OpenSettingsFromPause()   // НАСТРОЙКИ: спрятать меню, показать настройки
{

    settingsUi.SetActive(true);
}

```

Правило (задокументировано): карта из паузы паузу НЕ снимает — экран паузы прячется, время стоит, закрытие карты возвращает меню. Контроллеры общаются методами, а не читают внутренности друг друга.

## Вопросы, которые могут задать

**— Почему HUD обновляет скорость каждый кадр, а топливо/корпус — по событию?**
Скорость меняется непрерывно — её нечем «событийно» ловить, опрос дешевле. Топливо/HP меняются дискретно (в физическом шаге) — событие точнее и не дёргает UI зря.

**— Что такое CanvasGroup?**
Компонент, управляющий альфой/интерактивностью всей ветки иерархии разом (alpha, interactable, blocksRaycasts). Идеален для растворений UI и «неактивен, но Update работает».

**— Как сделать, чтобы UI работал во время паузы?**
Ничего специального: Update и так вызывается; лишь бы анимации/таймеры считались на unscaledTime/DeltaTime, а не на timeScale-зависимых (статья 1, таблица фаз).

## 10.1. Panel: анимация выезда по TAB

```csharp
private void Update()

private IEnumerator Slide(float targetX)
{
    float fromX = panel.anchoredPosition.x;
    for (float t = 0f; t < duration; t += Time.unscaledDeltaTime)   // пауза не мешает
    {
        float k = Mathf.Clamp01(t / duration);
        float eased = 1f - Mathf.Pow(1f - k, 3f);                    // ease-out cubic
        panel.anchoredPosition = new Vector2(Mathf.LerpUnclamped(fromX, targetX, eased),
                                             panel.anchoredPosition.y);
        yield return null;
    }
    panel.anchoredPosition = new Vector2(targetX, panel.anchoredPosition.y);
}
```

- Панель 480×1080 выдвигается из-за левого края: `hiddenX = −510`, `shownX = 0` (anchoredPosition — позиция RectTransform относительно якорей, статья 11 подробнее).
- **ease-out cubic** `1−(1−k)³`: анимация начинается быстро и «докатывается» — стандартная кривая для UI ( ease-in наоборот — разгоняется). Формула — обратный куб от остатка пути.
- `unscaledDeltaTime` — панель обязана работать на паузе (пауза её как раз показывает!).
- Повторное TAB во время анимации: `StopCoroutine(anim)` и новая анимация **от текущей позиции** (`fromX` считывается в начале) — плавная перенаправка, без скачка.
- `Keyboard.current.tabKey` — прямой опрос клавиатуры через Input System (без ассета действий — для одиночных UI-клавиш это допустимо и короче).

`Show(bool value)` — программное управление из паузы/карты: «нужное состояние уже стоит — ничего не делаем» (`if (value != shown) Toggle()`), чтобы Toggle не «проглотил» клик.

## 10.2. Factory: UI-каркас кодом на layout-группах

`OnboardComputerFactory.Build(panel)` строит всю панель: Шапка (заголовок, часы, деньги/рейтинг) → секция СОСТОЯНИЕ (5 строк + кнопка «ОТКЛЮЧИТЬ КОРАБЛЬ») → секция ЗАКАЗ (динамическая зона OrderArea + строка OrderPay) → секция СМЕНА (счётчики) → секция ЭФИР (плеер-заглушка).

Это «uGUI кодом». **Ликбез — система автоматической раскладки uGUI:**

- `VerticalLayoutGroup` / `HorizontalLayoutGroup` — компонент-контейнер, который **сам расставляет и растягивает детей** сверху вниз / слева направо. Детям не задаются позиции — контейнер всё вычисляет.
- Параметры `childControlWidth/Height` — контейнер управляет размерами детей; `childForceExpandWidth/Height` — остаток места делится между детьми.
- `LayoutElement` — ребёнок сообщает контейнеру пожелания: `minWidth/minHeight` (минимум), `preferredWidth/Height` (желаемое), `flexibleWidth/Height` (доля лишнего места; 1 = «забрать всю лишнюю ширину»).
- Типовая строка панели — HorizontalLayoutGroup c тремя детьми: фиксированной ширины (иконка), flexible=1 (текст — растянется), фиксированной (цифра).

Пример — строка заголовка и хелперы:

```csharp
public static GameObject H(string name, Transform parent)      // горизонтальный ряд
{
    var go = new GameObject(name, typeof(RectTransform));
    go.transform.SetParent(parent, false);                     // false = БЕЗ сохранения
    var layout = go.AddComponent<HorizontalLayoutGroup>();     // мировых координат
    layout.spacing = 8;
    layout.childControlWidth = true;
    layout.childControlHeight = true;
    layout.childForceExpandWidth = true;
    layout.childForceExpandHeight = true;
    layout.childAlignment = TextAnchor.MiddleLeft;
    return go;
}

public static void FixedSize(GameObject go, float width, float height)
{
    var le = go.AddComponent<LayoutElement>();
    le.minWidth = width;    le.minHeight = height;
    le.preferredWidth = width;  le.preferredHeight = height;
    le.flexibleWidth = 0f;  le.flexibleHeight = 0f;
}

public static void Flexible(GameObject go)
    => go.AddComponent<LayoutElement>().flexibleWidth = 1f;
```

`SetParent(parent, false)` — второй параметр worldPositionStability: false = «ребёнок сохраняет ЛОКАЛЬНЫЕ координаты» — единственно правильное для UI, иначе объект улетает (UI-иерархия живёт в координатах канваса).

Почему UI кодом, а не в редакторе: (1) каркас генерируется единообразно и перестраивается одной кнопкой; (2) карточки заказов — шаблоны, инстанцируемые N раз; (3) код — это документация: вся структура читается в `Build()`. private System.Collections.IEnumerator FadeIn(GameObject go)
```csharp
{
    for (float t = 0f; t < 1f; t += Time.unscaledDeltaTime / 0.18f)
    {
        if (go == null) yield break;              // уничтожен пересборкой — тихо выходим
        var group = go.GetComponent<CanvasGroup>();
        if (group == null) group = go.AddComponent<CanvasGroup>();
        group.alpha = t;
        go.transform.localScale = Vector3.Lerp(Vector3.one * 0.95f, Vector3.one, t);
        yield return null;
    }
    ...
}
```

Проверка `go == null` в каждом кадре корутины — Unity-переопределённый оператор ==: уничтоженный (Destroy) объект сравнивается с null, хотя C#-ссылка жива. Корутина, листингующая уничтоженный объект, — источник ошибок, отсюда выходы `yield break`.

## Вопросы, которые могут задать

**— Зачем две системы построения UI (фабрика + сцена)?**
Фабрика — источник структуры (код как генератор), сцена — результат для ручной доводки (инспектор удобнее для отступов и шрифтов). Binder поддерживает оба — это дешёвый фолбэк, а не дублирование.

**— Почему карточки строятся через Instantiate префаба, а не AddComponent-кодом?**
Префаб редактируется дизайнером в Prefab Mode (отступы, размер аватара) без пересборки. Код-путь остался как фолбэк — карточка строится и без префаба.

**— Что будет, если два предложения придут в один кадр?**
Обе карточки создадутся в одном RefreshOrder (цикл по orders.Offers), обе проиграют FadeIn параллельно, порядок — как в списке (`SetSiblingIndex(index)`).

**— Почему список предложений держится в Dictionary<OrderOffer, GameObject>?**
Диф карточек: `cardMap` сопоставляет offer → карточку. При RefreshOrder существующие карточки НЕ пересоздаются (не мигают): новые FadeIn, исчезнувшие FadeOut, остальные меняют порядок. Пересоздавать всё — проще, но мигание заметно глазу.

# Статья 11. Карты: миникарта и экран карты системы

**Файлы статьи:** `Assets/Scripts/UI/MinimapBinder.cs`, `MapScreenBinder.cs`, `MapScreenController.cs`.

Две карты, один принцип: **обе строятся кодом из LevelAsset** («не нарисованная копия» — комментарий в коде). Изменил уровень в редакторе — обе карты изменились сами. Общий for: перебрать `GravityField.Bodies` (миникарта — по живым объектам) / `level.Bodies` (карта — по данным).

## 11.1. RectTransform-ликбез (нужен для обеих карт)

UI живёт на канвасе в системе **якорей (anchors)**:

- У каждого RectTransform есть `anchorMin`/`anchorMax` — точка внутри родителя (0..1 по осям), к которой он «прикреплён», и `anchoredPosition` — смещение от этой точки в пикселях канваса.
- `sizeDelta` — размер. `offsetMin/offsetMax` — дистанции до якорных точек.
- «Растянуть на весь родитель» = anchorMin=(0,0), anchorMax=(1,1), offset'ы = 0 — этому соответствует хелпер `OnboardComputerFactory.Stretch` (статья 10).
- Для «позиция точки внутри карты» якорь ставят в центр родителя (0.5, 0.5), и тогда `anchoredPosition` — просто координаты от центра в пикселях. Именно это делают обе карты.

## 11.2. MinimapBinder — радар

Правило из комментария: «корабль всегда в центре, планета видна на экране => видна на радаре».

**Масштаб** — сколько пикселей на юнит мира:

```csharp
[Tooltip("Радиус охвата в юнитах мира (примерно половина видимой области камеры)")]
public float worldRange = 350f;

// В Update, один раз при готовности мира и layout:
pxPerUnit = bodiesRoot.rect.width * 0.5f / worldRange;
```

`worldRange = 350` юнитов ≈ полуэкран камеры в полёте (камера 320 высоты → ~470 ширины при 16:9 → половина ~235; взято с запасом — «примерно половина», комментарий честный). `rect.width` — рассчитанный размер RectTransform (сцена даёт `Bodies`-контейнер круглым; отсюда ожидание `rect.width >= 50` — «layout уже посчитан»).

**Каждый кадр — перенос точек:**

```csharp

    dots[i].anchoredPosition = ((Vector2)bodies[i].transform.position - center) * pxPerUnit;

// Стрелка по вектору скорости (спрайт остриём вверх)

{
```

Матрица преобразования «мир → радар»: `(world − shipPos) · pxPerUnit`. Корабль всегда (0,0). `−90°` у стрелки: спрайт нарисован остриём ВВЕРХ, а atan2 отсчитывает 0° от «вправо» — компенсация, та же идея, что `spriteNoseAngle` у корабля (статья 3).

## 11.3. MapScreenBinder — карта всей системы

Экранная карта по M. Построение один раз (`BuildMap`), дальше — только маркер корабля и ореол цели.

**Вписовать мир в прямоугольник:**

```csharp
private void BuildMap()
{
    // Границы мира -> вписываем в подложку с полем
    var bounds = new Bounds();
    bool first = true;
    foreach (CelestialBodyData body in level.Bodies)
    {
        var b = new Bounds(body.Position, Vector2.one * body.Radius * 2f);
        if (first) { bounds = b; first = false; }
        else        bounds.Encapsulate(b);       // раздвинуть границы до тела
    }
    bounds.Expand(200f);                          // поле от краёв
    worldCenter = bounds.center;
    scale = Mathf.Min(mapRect.rect.width / bounds.size.x,
                      mapRect.rect.height / bounds.size.y);

    foreach (CelestialBodyData body in level.Bodies)
        CreateBody(body);

    playerMarker = CreateCircle("PlayerMarker", 12f, Color.white, 100);
}
```

- `Bounds` + `Encapsulate` — стандартный способ «объять все объекты AABB-коробкой» (Axis-Aligned Bounding Box). Каждый тел — своя коробка размером 2r; коробка растёт, пока не вместит все.
- `scale = min(w/sizeX, h/sizeY)` — **вписывание с сохранением пропорций** (letterbox-подход): берем ограничение по более «тесной» оси, мир не искажается.
- `WorldToMap(world) = (world − worldCenter) · scale` — тот же аффинный перенос-масштаб, что у радара, только центр и масштаб фиксированы (карта — вся система, радар — окно вокруг корабля).

**Тела, названия, станции:**

```csharp
private void CreateBody(CelestialBodyData body)
{
    bool star = body.Type == BodyType.Star;
    // Планеты рисуются крупнее честного масштаба — карта не должна
    // быть пустой, читаемость важнее точных пропорций.
    float size = Mathf.Max(16f, body.Radius * 2f * scale * (star ? 1.6f : 1.9f));

    if (star)
    {
        RectTransform halo = CreateCircle(body.DisplayName + "Halo", size * 1.4f, ...);
        halo.anchoredPosition = WorldToMap(body.Position);   // иначе прилипнет к центру
    }

    RectTransform circle = CreateCircle(body.DisplayName, size, ...цвет...);
    circle.anchoredPosition = WorldToMap(body.Position);

    if (body.HasStation)                                     // жёлтая точка на краю
    {
        RectTransform station = CreateCircle(body.DisplayName + "Station", 10f, TaxiColor);
        station.SetParent(circle, false);
        station.anchoredPosition = new Vector2(size * 0.5f, size * 0.5f);
    }
    // + текстовая метка TMP над кругом
}
```

Коэффициент ×1.9 для планет — сознательная ложь масштаба: честные кружки на карте 2000×2000 юнитов были бы 3–4 пикселя. Комментарий фиксирует дизайн-приоритет: читаемость > точность. Маркер станции — дочерний к кругу планеты (двигается вместе с ней, если когда-нибудь планеты станут подвижными).

## 11.4. MapScreenController — клавиша M и сосуществование с паузой

```csharp
    var kb = Keyboard.current;
    if (kb == null) return;
    if (kb.mKey.wasPressedThisFrame)
        SetOpened(!opened);
    else if (opened && kb.escapeKey.wasPressedThisFrame)
    {
        SetOpened(false);
        EscJustClosed = true;                 // пауза: «ESC уже занят» (статья 9)
    }
}

private void SetOpened(bool value, bool force = false)
{
    if (!force && value == opened) return;
    opened = value;
    mapScreen.SetActive(opened);              // весь экран карты вкл/выкл
    onboard.Show(opened);                     // карта и борт.комп живут вместе

    if (pause != null)
    {
        if (opened) pause.NotifyMapOpened();  // пауза прячет своё меню
        else        pause.NotifyMapClosed();
    }
}
```

Связка «карта + бортовой компьютер» — дизайнерское решение: карта занимает экран, панель компьютера остаётся слева (такси-терминал). Дефолт `Start() → SetOpened(false, force: true)` — инициализация состояния единым методом.

## 11.5. Сравнение двух карт

| | Миникарта (радар) | Экран карты |
|---|---|---|
| Источник | живые объекты (`GravityField.Bodies`) | данные (`LevelAsset.Bodies`) |
| Центр | корабль (каждый кадр) | центр уровня (постоянный) |
| Масштаб | пиксели/юнит = const (350 юнитов охвата) | вписывание bounds в прямоугольник |
| Размеры тел | честные ×pxPerUnit, min 6 px | ×1.9 (планеты)/×1.6 (звёзды), min 16 px |
| Когда | всегда на экране | по M |
| Пульс цели | — (цель светится в мире) | да, unscaledTime |

## Вопросы, которые могут задать

**— Почему карта строится из LevelAsset, а радар — из объектов сцены?**
Карте нужны все тела, даже за экраном, и до начала игры — данные стабильны. Радару нужны живые позиции (объекты), и он всё равно ищет GravityField по тем же телам. Итого: статичный обзор — из данных, живой вид — из объектов.

**— Почему вы ждёте rect.width > 100 перед построением?**
Layout uGUI рассчитывается не мгновенно. У только что активированного объекта rect ещё нулевой; построить карту сразу = все тела слипаются в центре (масштаб мусорный). Ждём кадр, когда layout рассчитан.

**— Как масштабировать мир в пиксели?**
Аффинное преобразование: вычесть центр, умножить на масштаб. Для радара центр — корабль (динамика), для карты — центр bounds (константа).

## 12.3. Сохранение — что уже есть

Единственное сохранение в игре — громкости. Внутри AudioManager:

```csharp
// Файл: Assets/Scripts/Audio/AudioManager.cs
private static float LoadVolume(string key)  => PlayerPrefs.GetFloat("audio.vol." + key, 1f);

private static void SaveVolume(string key, float value)
{
    PlayerPrefs.SetFloat("audio.vol." + key, value);

}

// Общая громкость: квадратичная кривая — субъективно ровная.
public void SetMasterVolume(float linear01)
{
    float v = Mathf.Clamp01(linear01);
    AudioListener.volume = v * v;               // квадрат!
    SaveVolume("Master", v);
}
public float GetMasterVolume() => Mathf.Sqrt(AudioListener.volume);
```

**Ликбез — PlayerPrefs.** Встроенное хранилище «ключ-значение» (float/int/string), живёт в реестре Windows / plist macOS / файле в AppData. Для каждого ключа — значение по умолчанию (у нас 1f = 100%). `Save()` сбрасывает на диск (без него — на усмотрение Unity при выходе).

Ключи в игре: `audio.vol.Master`, `audio.vol.Music`, `audio.vol.Sfx`, `audio.vol.Ui`, `audio.vol.Engine`. Префикс «audio.vol.» — пространства имён для ключей (когда появятся сейвы прогресса, будут `save.` и т.п.).

**Почему v*v (квадрат)?** Громкость — логарифмическое ощущение: линейный ползунок в первой половине звучит как «почти всё ещё громко», реальная тишина сжата у нуля. Возведение в квадрат растягивает тихую половину — слайдер субъективно ровный. Классический психоакустический трюк (аналог шкалы дБ). Чтение — обратно корнем (`Sqrt`).

# Статья 13. Генерация фона: параллакс звёзд и процедурные спрайты

**Файлы статьи:** `Assets/Scripts/World/StarfieldParallax.cs`, `Assets/Scripts/Core/StubSprites.cs`, `Assets/Editor/StubSpriteBaker.cs`.

## 13.1. Задача

Космос между планетами без фона выглядит как «корабль стоит на чёрном». Решение — три слоя звёзд с **параллаксом**: дальние слои смещаются медленнее ближних, глазу есть опора — корабль «летит». Всё это без единого ассета: спрайты звёзд генерируются кодом.

## 13.2. StarfieldParallax — бесконечное поле без швов

Файл вешается на ту же Main Camera (статья 1). Три слоя:

```csharp
private void Awake()
{
    var cam = GetComponent<Camera>();
    float aspect = cam != null ? cam.aspect : 1.78f;

    // Тайл с запасом под самый широкий зум и монитор: звезда,
    // завернувшаяся за краем, не должна вспыхивать на экране.
    tileX = Mathf.Max(1300f, 2f * 250f * aspect + 400f);
    tileY = Mathf.Max(950f, 2f * 250f + 450f);

    Build(0.12f, 90, 0.28f, 0.38f);  // дальняя пыль: 90 звёзд, медленная
    Build(0.35f, 60, 0.48f, 0.52f);  // средний слой
    Build(0.65f, 36, 0.78f, 0.68f);  // ближние звёзды: 36, быстрые
}
```

`Build(factor, count, baseScale, alpha)`: создаёт корневой объект слоя, в нём `count` звёзд (SpriteRenderer + круг из StubSprites, случайный тёплый/холодный оттенок, случайные размер и альфа), каждой звезде — **seed**: случайная позиция внутри прямоугольника `±tile/2`. `factor` — доля скорости камеры (0.12 — почти неподвижная даль, 0.65 — заметно плывущие).

**Движение и заворачивание — каждый LateUpdate:**

```csharp
private void LateUpdate()
{
    // Якорь — камера БЕЗ тряски: дрожь ударов должна сдвигать мир
    // относительно фона, иначе тряску за звёздами не видно.
    var follow = CameraFollow.Instance;
    Vector3 anchor = follow != null ? follow.AnchorPosition : transform.position;

    foreach (Layer layer in layers)
    {
        // z = 0 обязательно: у якоря z камеры (−10) — слои попали бы
        // в плоскость самой камеры и отсекались near-плоскостью.
        layer.Root.position = new Vector3(anchor.x, anchor.y, 0f);
        Vector2 drift = (Vector2)anchor * layer.Factor;
        for (int i = 0; i < layer.Stars.Length; i++)
            layer.Stars[i].localPosition = Wrap(layer.Seeds[i] - drift);
    }
}

// Заворачивание в тайльный прямоугольник [-tile/2, tile/2].
private static float WrapAxis(float value, float tile)
{
    return (value % tile + tile) % tile - tile * 0.5f;
}
```

Механика:

1. **Корень слоя едет вместе с камерой** (`Root.position = anchor`) — слой всегда вокруг игрока.
2. **Звёзды дрейфуют внутри слоя** на `seed − anchor·factor`: для наблюдателя звезда сместилась назад на `(1−factor)·перемещение камеры` — чем меньше factor, тем «дальше» звезда. Формула параллакса: смещение экранного объекта обратно пропорционально расстоянию.
3. **Wrap (тайлинг по модулю):** звезда, ушедшая за край прямоугольника, появляется с противоположного. Разбор формулы `(v % tile + tile) % tile − tile/2`: в C# `%` может дать отрицательное (−5 % 3 = −2), поэтому сначала `+tile` и повторный `%` — результат всегда в [0, tile), минус половина — в [−tile/2, tile/2). Итог: поле звёзд **бесконечно и без швов**, звёзд всегда ~186 штук (90+60+36).
4. `z = 0` — деликатная деталь: у Main Camera z = −10 (камера «над» плоскостью игры). Если скопировать её z в слой, слой оказался бы в плоскости камеры и отсекался near clip plane. Компьютерная геометрия в одной строчке комментария.

**Почему LateUpdate и [DefaultExecutionOrder(50)]?** Камера встаёт в своём LateUpdate; фон обязан двигаться от **уже готовой** позиции камеры, иначе — дрожание на кадр. Атрибут `[DefaultExecutionOrder(50)]` сдвигает выполнение скрипта «позже всех» с дефолтным порядком 0: в пределах одной фазы (LateUpdate) порядок задаётся этим атрибутом. `AnchorPosition` (без тряски!) — иначе фон дрожал бы синхронно с миром, и тряска стала бы невидимой (статья 6.1).

Размер тайла с запасом (`2·250·aspect + 400`): самый дальний зум камеры — 470/2 = 235 юнитов полуширины; тайл шире экрана с запасом, чтобы звезда не «мигала» на границе в момент заворачивания.

## 13.3. StubSprites — спрайты из воздуха

Файл: `Assets/Scripts/Core/StubSprites.cs`. Статический класс-генератор текстур: круги (для планет, звёзд, частиц, звёзд фона), треугольник-корабль, капсула-чёрточка. Кэш по диаметру (`Dictionary<int, Sprite>`) — один и тот же круг не перегенерируется.

**Круг с обводкой и антиалиасингом:**

```csharp
public static Texture2D CreateCircleTexture(int size, float outlineWidth)
{
    var tex = new Texture2D(size, size, TextureFormat.RGBA32, true) { filterMode = FilterMode.Trilinear };
    var pixels = new Color32[size * size];
    var fill = new Color32(255, 255, 255, 255);      // белый — цвет даст SpriteRenderer.color
    var outline = new Color32(40, 40, 50, 255);      // тёмная кромка
    float pixel = 2f / size;                          // размер пикселя в [-1..1]
    for (int iy = 0; iy < size; iy++)
    for (int ix = 0; ix < size; ix++)
    {
        float x = (ix + 0.5f) / size * 2f - 1f;       // центр пикселя → [-1..1]
        float y = (iy + 0.5f) / size * 2f - 1f;
        float dist = Mathf.Sqrt(x * x + y * y);       // дистанция от центра
        float alpha = Mathf.Clamp01((1f - dist) / pixel + 0.5f);   // ← антиалиасинг
        Color c = dist > 1f - outlineWidth ? (Color)outline : (Color)fill;
        c.a = alpha;
        pixels[iy * size + ix] = c;
    }
    tex.SetPixels32(pixels);
    tex.Apply(true, false);       // загрузить в GPU (mipmaps — да, readable — нет)
    return tex;
}
```

Построчный разбор:

- Каждый пиксель текстуры — точка в нормированных координатах [−1..1] (пиксель 64×64 → сетка с шагом 2/64). `(ix+0.5f)` — **центр** пикселя, а не угол: иначе круг «сдвигался» на полпикселя и АА косил.
- `dist` — расстояние от центра; граница круга — dist = 1.
- **Антиалиасинг одной формулой:** `alpha = clamp01((1 − dist)/pixel + 0.5)`. Пиксели глубоко внутри (1−dist >> pixel) → alpha 1; глубоко снаружи → 0; ровно на границе — 0.5. Переход размыт ровно на один пиксель — нет «лестницы». Приём называется растеризация с покрытием: alpha = доля пикселя, накрытая кругом.
- Обводка: `dist > 1 − outlineWidth` — внешнее кольцо толщиной 8% радиуса темнее — читаемость силуэта планеты.
- Текстура **белая**: цвет накладывает `SpriteRenderer.color` (умножение в шейдере Sprites/Default) — одна текстура = любые цвета.
- `Apply(true, false)`: true — сгенерить mipmaps (корректное уменьшение вдалеке), false — не оставлять CPU-копию (экономия памяти; нам рисовать через SetPixels больше не нужно).

**Спрайт из текстуры с нужным мировым размером:**

```csharp
public static Sprite Circle(float diameter)
{
    int key = Mathf.Max(2, Mathf.RoundToInt(diameter));
    if (!circles.TryGetValue(key, out Sprite sprite) || sprite == null)
    {
        var tex = CreateCircleTexture(64, 0.08f);            // всегда текстура 64×64
        sprite = Sprite.Create(tex, new Rect(0f, 0f, 64f, 64f), new Vector2(0.5f, 0.5f),
                               64f / diameter);              // ← PPU = размер/diameter
        circles[key] = sprite;
    }
    return sprite;
}
```

Хитрость в `pixelsPerUnit = 64/diameter`: PPU — сколько пикселей текстуры в одном юните. 64 пикселя / PPU = диаметр в юнитах. Т.е. **одна и та же текстура 64×64 даёт круг любого мирового размера** — меняется только плотность пикселей. Pivot (0.5, 0.5) — центр. Отсюда `StubSprites.Circle(data.Radius * 2f)` у звёзд в WorldBuilder — спрайт ровно 2r юнитов.

**Треугольник и капсула** — через маску-функцию:

```csharp
public static bool InTriangle(float x, float y)
{
    float s1 = (-1.7f) * y - 0.7f * (x - 1f);
    float s2 = 0f * (y - 0.7f) - (-1.4f) * (x + 0.7f);
    float s3 = 1.7f * (y + 0.7f) - 0f * (x + 0.7f);
    return (s1 >= 0f && s2 >= 0f && s3 >= 0f) || (s1 <= 0f && s2 <= 0f && s3 <= 0f);
}

public static bool InCapsule(float x, float y)
{
    float dx = Mathf.Max(Mathf.Abs(x) - 7f, 0f);
    return dx * dx + y * y <= 1f;      // SDF-капсула: «прямоугольник + полукруги»
}
```

`InTriangle` — **метод знаков площадей**: три ребра треугольника как прямые; точка внутри, если она по одну сторону от всех трёх (все sᵢ ≥ 0 или все ≤ 0). `InCapsule` — упрощённая **signed distance function**: расстояние до отрезка/прямоугольника со скруглением ≤ радиуса. `CreateMaskTexture(size, inside)` красит белым то, что `inside(x,y)`, остальное — прозрачно.

## 13.4. StubSpriteBaker — из памяти в ассеты

## Вопросы, которые могут задать

**— Почему 3 слоя, а не 2 или 10?**
Глубина различима от ~3 планов (ближний/средний/дальний). Дальше — глаз не различает, только тратится fill rate.

**— Что такое параллакс физически?**
Смещение видимого положения объекта из-за движения наблюдателя, обратно пропорциональное расстоянию до объекта: ближняя звезда (factor 0.65) летит по экрану быстро, дальняя пыль (0.12) почти стоит.

**— Почему звёзды не GetComponent в Update, а кэш в списках?**
`layer.Stars[i]` — массив Transform, заполненный один раз в Build. Поиск компонентов каждый кадр — расточительно; ссылки кэшируются при создании.

**— Как одна белая текстура даёт разные цвета?**
Цвет вершин/спрайта умножается на текстуру в шейдере: белая текстура (1,1,1) — нейтральный множитель. Один материал — тысячи цветных вариаций без доп. памяти.

**— Mipmaps — что это?**
Пирамида уменьшенных копий текстуры (1/2, 1/4, ...). Когда объект далеко и текстура занимает мало пикселей, GPU берёт готовую маленькую копию — без мерцания и шума под-Найквиста.

## 14.3. Три вида звуков

**а) One-shot (щёлчки, взрывы) — из пула:**

```csharp
public void PlayOneShot(SoundId id, float intensity = 1f)
{
    SoundEntry entry = GetEntry(id);
    if (entry == null || entry.Loop) return;

    AudioSource src = GetFreeOneShotVoice();          // свободный из пула (макс 12)
    src.clip = ChooseClip(entry, intensity);          // вариация: по силе или случайно
    src.pitch = entry.Pitch * (1f + Random.Range(-entry.PitchJitter, entry.PitchJitter));
    src.volume = entry.Volume * GroupFactor(entry.Group) * Mathf.Clamp01(intensity);
    src.panStereo = 0f;
    src.loop = false;
    src.Play();

    if (id == SoundId.Explosion)
        DuckAll();                                    // взрыв «срезает» остальное
}

private AudioSource GetFreeOneShotVoice()
{
    foreach (AudioSource src in oneShotPool)
        if (!src.isPlaying) return src;
    if (oneShotPool.Count >= MaxOneShotVoices)
        return oneShotPool[0];   // переполнение — перебиваем старейший занятый
    AudioSource voice = CreateVoice("OneShot");
    oneShotPool.Add(voice);
    return voice;
}
```

Громкость звука = произведение: `Volume(записи) × громкость группы × duck × интенсивность` — конвейер микшера. Пул голосов: у Unity есть лимит одновременно играющих AudioSource; 12 голосов хватает, при переполнении перебивается первый — дешёвая политика «новое важнее».

**б) Лупы (двигатели, жар) — словарь голосов с фейдами:**

```csharp
public void StartLoop(SoundId id)
{

    {
        if (voice.FadingOut)     // вернули из затухания
        { ...прервать фейд, фейд обратно... }
        return;
    }
    voice = new LoopVoice { Entry = entry, Source = CreateVoice("Loop_" + id) };
    voice.Source.clip = ChooseClip(entry, 1f);
    voice.Source.loop = true;
    voice.Source.volume = 0f;                    // старт с нуля — фейд 0.15с
    voice.Source.Play();
    loops.Add(id, voice);
    voice.Fade = StartCoroutine(FadeLoop(voice, 1f));
}

// Интенсивность лупа: громкость и тон (двигатель «гудит сильнее» на тяге)
public void SetLoopIntensity(SoundId id, float intensity)
{
    if (!loops.TryGetValue(id, out LoopVoice voice) || voice.FadingOut) return;
    voice.Intensity = Mathf.Clamp01(intensity);
    ApplyLoopParams(voice);
}

private void ApplyLoopParams(LoopVoice voice)
{
    float i = voice.Intensity;
    float vol = LoopVolumeMin + (1f - LoopVolumeMin) * i;      // 0.4..1 — не в ноль
    voice.Source.volume = voice.Entry.Volume * GroupFactor(...) * vol;
    voice.Source.pitch = voice.Entry.Pitch * (LoopPitchMin + LoopPitchRange * i); // 0.9..1.12
}
```

Луп-голос — объект класса `LoopVoice` (Source + Entry + Intensity + Pan + фейд-корутина) в словаре по SoundId: `SetLoopActive(EngineMain, true/false)` — включить/выключить, интенсивность 0..1 маппится одновременно в громкость И питч (приём «двигатель ревёт» — рост тона убедительнее роста громкости). Фейды 0.15 с на старте/стопе — резкое включение лупа слышно как щелчок.

**в) Музыка — кроссфейд двух голосов:**

```csharp

{
    if (id == currentMusic) return;
    ...
```

Классический **crossfade**: пока один AudioSource за 1.5 с набирает громкость, второй её отдаёт. Два голоса + счётчик-переключатель (flip) — простейшая реализация без библиотек. Смена сцены: SceneMusic новой сцены вызывает PlayMusic с другим id → кроссфейд.

**Ducking** — «приглушение при важном»:

```csharp
{

            groupDuck[g] = DuckFactor;          // двигатели/эффекты → 20%
```

Приём из радиовещания (ducking = «пригнуть» музыку, когда говорит диктор): взрыв на секунду приглушает всё, кроме музыки/UI — внимание игрока на взрыв. Множитель duck сидит в `GroupFactor` — общей формуле громкости, поэтому приглушается и уже играющее, и новые звуки.

## Вопросы, которые могут задать

**— Почему AudioSource'ы — дети AudioManager'а?**
Голоса (`CreateVoice` → `go.transform.SetParent(transform)`) умирают вместе с менеджером, не мусорят сцену и не теряются (DontDestroyOnLoad наследуется детьми).

**— Чем loop-звук отличается от one-shot?**
Loop играет непрерывно и управляется (интенсивность/панорама/фейды) — это «канал» с состоянием. One-shot — «выстрелил и забыл». В каталоге их разделяет флаг Loop, в менеджере — разные хранилища (словарь vs пул).

**— Что такое панорама (panStereo)?**
Баланс левый/правый канал −1..+1. Для стрейфа задумано: маневровые слева/справа двигателей звучат со своей стороны. Сейчас закомментировано вместе с эффектами.

**— Почему музыка не через PlayOneShot?**
Музыка должна кроссфейдиться при смене трека (два голоса), не иметь джиттера тона и не попадать подducking (взрыв не глушит музыку). Отдельный механизм под отдельные требования.

## 15.3. Стрелки, snap, копипаст

## 15.4. Живая валидация

`Validate(level)` возвращает список предупреждений (в окне — жёлтые HelpBox'ы). Правила и их смысл:

| Проверка | Зачем |
|---|---|
| центры двух тел ближе 260 | слишком близко — гравитация тел «порвёт» игрока |
| поверхности пересекаются | `d < r1 + r2` — визуальный и физический баг |
| жар звезды ближе 550 к спавну | старт в жаре = мгновенный урон |
| жар задевает планету | посадка на такую планету будет обжигать |
| стартовая «планета» — звезда | спавн на звезде смертелен |
| спавн внутри планеты (< r+7) | корабль застрянет в коллайдере |
| радиус планеты вне 15–40, звезды вне 46–64 | нормы из дизайн-дока 09_LEVEL_DESIGN |

Философия (в комментарии): **предупреждения, не запрет** — редактор не ломает эксперименты, но подсвечивает риски. Валидация вызывается каждый OnGUI — предупреждения «живые», исчезают по мере исправления.

## 15.5. SceneView-гизмо

`LevelEditorSceneView` — статический класс с `[InitializeOnLoad]`:

```csharp
[InitializeOnLoad]
public static class LevelEditorSceneView
{
    static LevelEditorSceneView()
    {
        SceneView.duringSceneGui += OnSceneGui;    // крючок на отрисовку сцены
    }
    ...
}
```

**[InitializeOnLoad]** — «выполнить статический конструктор при загрузке домена» (при старте редактора и после каждой перекомпиляции). Статический конструктор подписывается на `SceneView.duringSceneGui` — коллбек отрисовки поверх сцены. Итог: класс без единого поля инстанса живёт всегда, пока открыт проект.

**Что рисуется** (Handles API — примитивы редактора: `DrawSolidDisc` залитый круг, `DrawWireDisc` окружность, `DrawDottedLine` пунктир, `DrawPolyLine` ломаная, `Label` текст):

- тела: заливка + контур (звезда жёлтая, планета голубая) + имя + «станция»;
- **превью спрайта** — если у тела задан Visuals.Sprite, он рисуется прямо в гизмо через `GUI.DrawTextureWithTexCoords` с пересчётом мира в координаты GUI (`HandleUtility.WorldToGUIPoint`) — дизайнер видит настоящий арт, а не абстрактный круг;
- **посадочное кольцо** (зелёный пунктир) и **кольцо захвата** (голубой мелкий пунктир) — те же формулы, что в игре: `landing = r + LandingRingOffset`, `capture = r·CaptureRingK + CaptureRingBase`; константы берутся из PhysicsConfig (поиск `AssetDatabase.FindAssets("t:PhysicsConfig")` с кэшем на 5 секунд — FindAssets тяжёлый, а зовётся из отрисовки);
- **жар** — оранжевый пунктир + еле заметная заливка;
- **линии от выбранного тела** до всех остальных с подписями дистанций, < 300 — красным;
- **спавн** — треугольник на планете старта под углом SpawnAngleDeg + стрелка курса;
- **рамка камеры** — прямоугольник «что видит игрок» (320×16/9 из CameraFollow) вокруг спавна;
- **граница системы** — красный пунктир радиуса WorldRadius;
- сетка 100 юнитов (тоггл);
- **гравиполе** (тоггл): стрелки каждые 150 юнитов, длина и цвет — по величине суммарного ускорения в точке;
- **зонд гравитации** (Ctrl): под курсором стрелка «куда потянет» + число ед/с²;
- **траектория взлёта** (тоггл): симуляция 6 секунд свободного полёта после стартового импульса 85 (та же формула гравитации, шаг 1/60, стоп при столкновении).

Гравитация в редакторе — **копия формулы игры** (`GravityAt`: `min(k·r·m/d², clamp)`, суммирование по телам) — редактору нельзя зависеть от рантайм-сцены (тел в ней нет), а дублировать формулу в editor-коде — плата за независимость инструментов от плеймода. Если менять формулу — менять в двух местах (наш известный техдолг).

**Мышь: выбрать и таскать:**

```csharp
private static void HandleDrag(LevelEditorWindow window, LevelAsset level)
{
    Event ev = Event.current;
    if (ev.type == EventType.MouseDown && ev.button == 0 && !ev.alt)
    {
        Vector2 world = MouseWorld(ev.mousePosition);
        int hit = FindBodyAt(level, world);          // клик внутри радиуса тела
        if (hit >= 0)
        {
            window.SetSelected(hit);
            dragging = true;
            dragOffset = level.Bodies[hit].Position - world;   // за какую точку держим
            Undo.RecordObject(level, "Move Body");   // undo на весь drag целиком
            ev.Use();
        }
    }
    else if (ev.type == EventType.MouseDrag && dragging)
    {
        Vector2 pos = MouseWorld(ev.mousePosition) + dragOffset;
        if (window.SnapEnabled && !ev.shift)
            pos = ... snap 10 ...;
        level.Bodies[index].Position = pos;
        dragPosition = pos;
        EditorUtility.SetDirty(level);
        ev.Use();
    }
    else if (ev.type == EventType.MouseUp && dragging) { dragging = false; ev.Use(); }
    ...
}

private static Vector2 MouseWorld(Vector2 mouse)
{
    Ray ray = HandleUtility.GUIPointToWorldRay(mouse);   // пиксель экрана → луч
    return new Vector2(ray.origin.x, ray.origin.y);      // в 2D — начало луча
}
```

- `!ev.alt` — Alt в Scene View занят навигацией орбиты, не перехватываем.
- `dragOffset` — курсор держит тело за ту точку, за которую схватил (без этого тело «прыгало» бы центром на курсор).
- `Undo.RecordObject` один раз на MouseDown → вся цепочка MouseDrag — одна операция отмены (Ctrl+Z откатит весь перенос, а не каждый пиксель).
- Рядом с тащимым телом — живые координаты `(x, y)`.

## Вопросы, которые могут задать

**— Почему редактор не работает в билде?**
Папка Assets/Editor компилируется только в редакторе Unity (сборка Assembly-CSharp-Editor не включается в билд). Типы UnityEditor.* в билде недоступны.

**— Чем Handles отличается от GUI?**
GUI — Immediate Mode для окон (кнопки/поля, координаты — пиксели окна). Handles — рисование в 3D/2D-мире сцены (координаты — мировые), плюс утилиты вроде GUIPointToWorldRay. В Scene View живут оба.

**— Почему EditorUtility.SetDirty нужен, ведь объект же изменился?**
Изменение поля в памяти ничего не значит для системы ассетов: Unity сохраняет только «грязные» объекты. SetDirty — заявка «этот ассет надо сохранить». SerializedObject-паттерн делает это сам.

**— Как сделать undo у своего инструмента?**
Undo.RecordObject(цель, метка) ДО изменения — снапшот; для создаваемых объектов — Undo.RegisterCreatedObjectUndo; для удаления — Undo.DestroyObjectImmediate. У нас используются первые два.

**— Зачем кэш PhysicsConfig на 5 секунд?**
AssetDatabase.FindAssets сканирует базу ассетов — дорого. Гизмо рисуются десятки раз в секунду; без кэша редактор бы подтормаживал. 5 секунд — баланс свежести и скорости.

## А.5 Известные упрощения (честные ответы «почему так»)

1. Гравитация — Эйлер без симплектики: орбиты медленно «дышат», для аркады неважно.
2. Формула гравитации продублирована в LevelEditorSceneView.GravityAt — редактор не зависит от рантайма ценой копипасты.
3. Планеты статичны (нет орбит) — иначе прогноз траектории и карта усложняются.
4. Связка «планета сцены ↔ планета данных» по имени строки — переименование ломает заказы/респавн.
5. Эффекты звука выключены (решение 2026-09-20), музыка играет; инфраструктура готова.
6. Деньги/рейтинг/экономика — нули в UI, расчёта нет. Continue без сейва.
7. Fuel — свойство с событием, Hp — public поле (эволюция кода).

## А.6 Мини-словарь терминов (если спросят «а что такое X?»)

**MonoBehaviour** — базовый класс «компонента игры» (жизненный цикл Awake/OnEnable/Start/Update/...). **ScriptableObject** — сериализуемый ассет-данные. **Префаб** — шаблон объекта. **Instantiate** — создать экземпляр. **FixedUpdate** — шаг физики (0.02 с). **timeScale** — масштаб игрового времени (0 = пауза). **unscaledTime** — время без учёта timeScale. **Корутина** — метод с yield return, исполняемый по частям. **Событие (event/Action)** — механизм «кто хочет — узнает». **Замыкание** — лямбда, захватившая переменные. **Якоря RectTransform** — система привязки UI к родителю. **Layout-группа** — автогруппа детей UI. **sortingOrder** — порядок отрисовки спрайтов. **orthographicSize** — половина высоты ортокамеры в юнитах. **PPU** — пикселей на юнит. **Кламп/лерп** — ограничение/интерполяция. **Пул объектов** — переиспользуемые объекты вместо Instantiate. **Undo.RecordObject** — снапшот для Ctrl+Z в редакторе. **DontDestroyOnLoad** — не удалять при смене сцены. **Singleton** — единственный экземпляр + глобальный доступ.
