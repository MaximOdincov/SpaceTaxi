## РЕЖИМ И СРЕДА — нюансы, на которых прожглись в Н4 (читай внимательно)

### Ноутбук: сон и питание
- Windows уводит ноутбук в сон — редактор и CLI-соединение умирают, субагенты зависают на
  мёртвом сокете. Признак: eval падает по таймауту, повторно тоже.
- Действия оркестратора: (1) проверь, что питание от сети и крышка открыта — в начале сессии
  проверь `powercfg /q SCHEME_CURRENT SUB_SLEEP STANDBYIDLE` (таймаут сна; если не ноль —
  упомяни в логе как риск, сам системные настройки владельца не меняй без необходимости);
  (2) при зависании CLI — пробуй команду ещё раз; если соединение не оживает — см. пункт про
  перезапуск редактора ниже; (3) не оставляй длинных пауз между касаниями редактора.

### Релей пайплайна гасит редактор (важно!)
- com.unity.pipeline поднимает в редакторе сервер для unity-cli. При разрыве CLI-соединения
  релей через **180 с** неактивности ПЛАВНО ЗАКРЫВАЕТ РЕДАКТОР («Auto-shutdown timer fired…
  shutting down: Dedicated client disconnected» — это реально произошло в Н4, редактор умер).
- Симптомы: `EDITOR_NOT_RUNNING` в ответах CLI; процесс Unity.exe то исчезает, то появляется
  новый с маленькой памятью (грузится).
- Действия: `unity open "<путь проекта>" --editor-path "C:\Unity\6000.6.8f1\Editor\Unity.exe"`,
  затем поллинг `script eval "return \"alive\""` каждые ~25 с до подъёма сервера (это минуты),
  убедись, что сцена — GameScene (`OpenScene` через eval), затем `unity recompile`.
- Вывод: касайся редактора регулярно; длинные субагентные работы (аналитика, ревью) — норм, но
  между ними делай лёгкий keep-alive eval, чтобы релей не заснул.
- При падении редактора возможна папка `Assets/_Recovery/` — не коммить её, покажи владельцу.

### Плей-луп и замеры
- Плей-луп редактора без фокуса стоит на 1 кадре; `Application.runInBackground=true` в редакторе
  НЕ оживляет фоновый луп. Все живые проверки — через `UnityEditor.EditorApplication.Step()`
  внутри `script eval` (1 вызов ≈ 1 кадр).
- Корутины/анимации (слайды, счётчики) на Step-ах могут не доходить до конца (unscaledDeltaTime
  мал). Для проверки UI выставляй состояние напрямую (позиция/параметр) → Step → скриншот.
- Скриншоты: `UnityEngine.ScreenCapture.CaptureScreenshotAsTexture()` — работает после фокуса
  GameView (`GetWindow(GameView)` + `Focus()` + `Repaint()`) и требует ≥1 отрендеренного кадра
  (свежий плей может отдать null — сделай цикл Step+Repaint перед снятием). Сохраняй в
  `<проект>/Temp/`, в лог пиши путь. `unity command screenshot --view game` рендерит камеру
  БЕЗ UI.
- Пример рабочего снимка UI (проверено в Н4): eval с фокусом → цикл «Step + RepaintAllViews» →
  CaptureScreenshotAsTexture → File.WriteAllBytes PNG → уничтожить текстуру.

### Верификация (команды)
```bash
unity recompile --project-path "<корень>" --format json   # ждать errors:0 (успех: data.summary)
unity command editor.playmode start|stop --project-path "<корень>"
unity command script eval --caller plugin --skill unity-cli '<C# с return строки;>'
```
- В eval: `new string(' ',n)` — кавычки-ЧАРЫ, не строки; Python-парс ответов: `python -X utf8`
  (кириллица/Đ); не пиши диагностические json-дампы в корень проекта — чисти за собой ПЕРЕД
  коммитом (в Н4 дважды чуть не уехали в историю).
- Bash-файлы, создаваемые сессией, держи вне проекта или в tools/ (в репо — только осознанные).

### Домашние правила кода
- **TMP + Ellipsis режет текст и по вертикали**: высота узла ≥ fontSize×1.32, иначе 0 видимых
  символов («есть, но невидим» — болели этим в Н4). Проверено: JetBrainsMono 36pt ≈ 47.5px.
- Якоря: левая колонка HUD — top-left (0,1) с pivot x=0 (anchoredPosition.x = левый край);
  выравнивание колонки статов — по FuelIcon (x=14.2).
- Кнопки: `UiSfx.Hook(button)` первым хуком; тёмные тексты на ярких кнопках — `ActionTextColor`.
- Цвета/константы UI — из `OnboardComputerFactory` (публичные), не плодить свои дубли без надобности.
- Правки `.asset` — через `SerializedObject` из eval (сохраняет GUID/fileID); YAML руками — только
  если через редактор нельзя.
- Физика в FixedUpdate; симметричная отписка событий; null-check после GetComponent;
  `[SerializeField] private`, никаких public fields.

## ЗАДАЧИ Н5 (сгруппированы; порядок исполнения — в конце)

### Группа A — механика и физика (первая волна)

**A1 (№2). Щит-иконка — вернуть `shield_icon`.** В Н4.13 я поставил `Art/icons/shield` — владелец
хочет `Art/icons/shield_icon`. В `HudBinder.BuildStatIcons` поменять путь обратно. Приёмка:
скриншот HUD (щит с обводкой, как в Н4.12), compile 0/0.

**A2 (№14). Убрать отсутствие топлива на заправках.** «Это подстава». Механика outage больше не
используется: `FuelOutageChancePct = 0` в PricingConfig_Default (поле оставить — карта/логи ссылаются),
проверить, что `FuelNetwork.OutageStations` при 0% даёт пустое множество, UI станции/тосты/карта
не показывают «топлива нет». Сток `FuelStockFractionByTier` оставить (бедные продают меньше, но
есть всегда). Приёмка: eval `OutageStations(...).Count == 0` на живом уровне; экран станции обычный.

**A3 (№13). Убрать «ускорение от пролётa рядом с планетами».** Это дискретный буст «качелей»:
в `ShipController.FixedUpdate` при входе в capture-ring планеты скорость умножается на
`ship.Eff.GravityBoost` (`velocity *= ship.Eff.GravityBoost`). Убрать этот буст ДЛЯ ПЛАНЕТ; для
звёзд и чёрных дыр качели оставить (BlackHole.cs, звёздная гравитация не трогаются). Сама гравитация
планет остаётся (на ней посадка). Приёмка: eval-замер скорости до/после пролёта capture-ring
планеты — прироста буста нет; полёт не сломан (прогон до соседней планеты).

**A4 (№6). Дрожание линии пути (dashes) на орбите.** При закручивании вокруг планеты дэши
«дрожат». Копать в `TrajectoryPredictor`: подозреваю `smoothSpacing` lerp + пересчёт позиций
каждый кадр при кривом прогнозе (симуляция меняется → точки прыгают). Решение на выбор: считать
дэши строго от стабильного шага (фиксированный spacing, без lerp), кэшировать прогноз и
пересчитывать реже (раз в N кадров или при изменении скорости > порога), или сглаживать только
длину, не позиции. Главное — линия стабильна на орбите. Приёмка: eval-замер позиций дэшей в
двух соседних кадрах на орбите — расхождение < ~0.5 юн; визуально на скриншоте линия ровная.

**A5 (№3). Посадка: «садится слишком поздно — глубоко заходит, потом резко подпрыгивает».**
Сейчас телепорт снапа срабатывает по контакту капсулы, а видимый спрайт успевает зайти в планету,
потом резкий подъём на посадочную позу. Требование владельца: «ровно садился и закреплялся без
подпрыгиваний». План: в `LandingSystem` (OnCollisionEnter2D → Land) — (а) проверь момент снапа:
contact point vs посадочная поза (`ShipPlacement`); (б) вместо мгновенного телепорта сделай
короткий дожим: корутина 0.1–0.15 с плавно доводит позицию до `planet.Radius + LandedExtent`
(Linear/Smootstep по unscaledDeltaTime), состояние LandedOn включить сразу (управление/физика
выключены), физтель заморозить на время дожима; (в) проверь `HullSystem.RespawnAfter` и
`SaveSystem.RestoreShip` — там телепорт сразу, это ок (нет контакта). Не сломать взлёт. Приёмка:
скриншоты последовательности посадки (3 кадра Step-ами) — без провала под поверхность и без
скачка; посадка с разных скоростей (быстро/медленно).

**A6 (№9). Заказ на планете пассажира — мгновенная посадка пассажира.** Если при принятии заказа
корабль стоит на той же планете, что пассажир (`ship.LandedOn == offer.From`-планета) — пассажир
садится сразу (без повторного «приземления»): вызвать тот же путь, что при физической посадке
пассажира (найди в OrderService/LandingSystem, как засчитывается pickup), плюс тост/обновление
панели. Приёмка: взять заказ стоя на планете — пассажир в салоне, активный заказ перешёл в
«везу», без телепортов.

**A7 (№10). Ореол выбранной планеты.** Сейчас на цели появляется огромный жёлтый круг-ореол ПОД
планетой («планета подчёркнута огромным кругом и держит своего пульсирующего брата» — это
CaptureRing/TargetRing-подчёркивание). Убрать большой круг; оставить компактный жёлтый
пульсирующий ореол вокруг планеты (масштаб ≈ посадочное кольцо или чуть больше тела, пульс
альфой/масштабом). Найти рендер в WaypointIndicator/миникарте/HUD (мировой маркер цели). Приёмка:
скриншот цели — маленький пульсирующий ореол, никакого огромного круга.

(сейчас «на чуть-чуть»). Слайдер оставить. Сумму показывать со значком валюты (Đ), не словом
«кредиты». ОДНА кнопка: «ЗАПРАВИТЬ ДО ПОЛНОГО» (пресеты убрать). Шрифт кнопки светлее (BrightColor
или белый). Приёмка: скриншот заправки (полная ширина ячеек, одна кнопка, хедер с кредитами,
крестик), заправка работает.

**C2. Магазин кораблей.** Раскладка: слева — характеристики (таблица статов), справа — БОЛЬШОЙ
красивый корабль (спрайт из `Art/ships/`, показать с выбранной расцветкой). Внизу — полоска
навигации: [←] Название корабля [→] (стрелки меньше, чем сейчас). «ВЫ ЗДЕСЬ» убрать.
Под характеристиками — выбор расцветки (свотчи/стрелки — механика FlipPaint уже есть в
StationScreenController, перетащить в новый UI).
Статы-сравнение: полоска показывает рассматриваемый корабль, **риской-маркером — твоё текущее
значение** на той же полоске; отрезок между твоим и рассматриваемым значением подкрашивается —
красный, если рассматриваемый хуже, зелёный, если лучше (стандарт жанра; владелец спрашивал).
«Тормозной путь» переименовать в положительную метрику — «Мощность торможения» (Retro: больше =
лучше), чтобы ВСЕ статы читались «больше = лучше». Приёмка: скриншоты магазина (2 разных корабля),
покупка работает, покраска меняется.

**C3. Улучшения.** Механику пересмотреть: улучшения — «эффективные, но не сильно, и дешёвые»
(рекомендации BALANCE_N4: цена уровня ≈ Δдоход×10; см. лист «Инварианты»). UI — как магазин:
список улучшений (линии: Двигатель/Бак/Корпус/Манёвренность и т.п.), у каждого — +статы на
полосках (как в магазине), цена в Đ, кнопка покупки. Продумай состав улучшений и их дизайн
(например: двигатели дают тягу/возможность дальних перелётов, бак — запас, корпус — прочность,
манёвренность — стрейф; можно добавить минусы лёгкие: +тяга = чуть больше расход — у владельца
была такая идея, реши по месту и задокументируй). Приёмка: скриншот экрана улучшений, покупка
меняет статы (проверить в коде, что Eff пересчитывается), цены в конфиге.

**C4. Ремонт.** Правила мастерских по тирин-гам (данные HasRepair/RepairTier уже есть):
бедные (T1) ремонтируют корабли тиров 1-2, средние (T2) — 1-3, лучшие (T3+) — 4-5; наценка выше
в лучших мастерских (коэффициент по RepairTier в конфиг). UI — как улучшения: полоска состояния
корпуса, цена ремонта в Đ, кнопка «Починить». Приёмка: скриншот, ремонт работает, корабль ниже
допустимого тира НЕ чинится (показать сообщение), баланс наценок в конфиге.

### Группа D — заказы и баланс

**D2 (№11). Прогрессия заказов.** Система: старт — заказы только из бедного района и рядом с

часть заказов доступна только хорошим кораблям (гейт по тиру); иногда подкидывать сложные
(дальние/с заданиями), но высокооплачиваемые. Реализация: у OrderService пулы офферов
взвесить по (сектор, тир корабля, рейтинг); гейт-фильтр по тиру корабля; шанс «жирного» заказа
растёт с рейтингом. Числа — в конфиг (PricingConfig/OrderService настройки), не хардкод; сверить
с моделью tools/balance_n4 (доход/заказ по районам). Приёмка: на старте (Яйцо) — только близкие
бедные заказы; после «прокачки» через DebugCheats (рейтинг/корабль) — открываются дальние; жирные
