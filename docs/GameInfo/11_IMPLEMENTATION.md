## 2. Поток игры: от запуска до полёта

1. **MainMenu.unity** — камера (SolidColor #05060F), `AudioManager` (создаётся здесь,
   `DontDestroyOnLoad` — переживает смену сцены; дубль из GameScene самоуничтожается,
   `AudioManager.Awake`), `SceneMusic` (включает MusicMenu), UI-терминал меню,
   `SceneFlowButtons` (переходы), `SettingsScreenController` (настройки).
2. Кнопка **«НОВАЯ ИГРА»** → `SceneFlowButtons.StartNewGame()` → `SceneManager.LoadScene("GameScene")`.
3. **GameScene.unity** стартует. Порядок инициализации ключевых объектов:
   - `AudioManager` (дубль) — видит живой Instance, уничтожает себя.
   - `GameSession.Start()` (файл `Scripts/Core/GameSession.cs`) — точка сборки мира:
     создаёт `WorldBuilder(level, physicsConfig, input, planetPrefab, shipPrefab)` и зовёт `Build()`.
   - `WorldBuilder.Build()` (`Scripts/World/WorldBuilder.cs`):
     1. `new GameObject("GravityField")` — реестр тел **создаётся первым**;
     2. для каждого тела из `LevelAsset.Bodies` — `CreateBody()`: инстанс префаба
        Planet (или объект-звезда кодом), `CelestialBody.Init(data, config)` —
        при `OnEnable` тело само регистрируется в `GravityField`;
     3. `CreateShip()` — инстанс `Ship.prefab` (в нём уже: SpriteRenderer, CircleCollider2D
        r=4, Rigidbody2D (Continuous, Interpolate), Ship, ShipController, ShipAudio,
        LandingSystem, HeatAudio, HullSystem, TrajectoryPredictor), позиция на
        поверхности планеты старта, `State = Landed`, `LandedOn = планета старта`.
   - `GameSession` вешает на `Camera.main` компонент `CameraFollow` и даёт ему цель.
4. Игрок стоит на планете. Жмёт **W** → `ShipController.Update()` ловит нажатие
   (взлёт обрабатывается в Update, а не FixedUpdate — `WasPressedThisFrame` между
   физическими шагами теряется) → `LandingSystem.Takeoff()` — импульс 85 от центра
   планеты → `State = Flying` → далее каждый `FixedUpdate` работает физика (раздел 3–4).

**Почему сцена «почти пустая», а мир строится кодом:** уровень — это данные
(`LevelAsset`), а не нагромождение объектов в сцене. Один и тот же код строит
любой уровень; редактор уровня пишет в те же данные. Поменять уровень = поменять
одну ссылку в инспекторе `GameSession`.

## 3. Физика полёта — гравитация

### Где в коде

- `Scripts/Physics/GravityField.cs` — реестр тел и суммарное ускорение (`GetAccelerationAt`).
- `Scripts/Physics/ShipController.cs`, `FixedUpdate()` — применение гравитации и управление.
- `Scripts/Physics/PhysicsConfig.cs` + ассет `ScriptableObjects/PhysicsConfig_Default.asset` — все константы.

### Формула

Для каждого тела считается ускорение по закону обратных квадратов и суммируется
(принцип суперпозиции полей — как в реальности):

```csharp
// GravityField.GetAccelerationAt
float a = Mathf.Min(config.GravParamOf(body) / d2, config.GravityAccelClamp);
accel += delta / d * a;   // вектор к телу, длиной a
```

- Гравитационный параметр тела: `GravParamOf(body) = GravityParamK · Radius · MassMultiplier`
  (в ассете `K = 52000`; планеты `MassMultiplier = 1`, звёзды `4.5`).
- `d` — расстояние до центра тела, ускорение ∝ `1/d²` — форма закона ньютоновская.
- `GravityAccelClamp = 240` — потолок ускорения от одного тела (зачем — см. раздел 5).

В `ShipController.FixedUpdate()`:

```csharp
velocity += gravity.GetAccelerationAt(pos, config) * dt;   // гравитация
... // управление (раздел 4)
ship.Body.linearVelocity = velocity;                        // отдаём движку
```

### Ключевые параметры (актуальные значения ассета)

| Параметр | Значение | Смысл |
|---|---|---|
| GravityParamK | 52000 | масштаб гравитации (прототип 26000; ×2 — решение после плейтеста: планеты «ощутимо тянут») |
| GravityAccelClamp | 240 | предел ускорения от одного тела |
| Thrust | по модели (ShipConfig) | тяга W; сток 95, линейка 88–140 |
| Retro | 80 | торможение S (2026-10-03: было 115 — тормозить было слишком легко) |
| StrafeAcc | по модели (ShipConfig) | боковая тяга A/D; сток 130 (прототип 85 — слабо) |
| StrafeMaxTurnRate | 60°/с | предел скорости поворота вектора от стрейфа |
| MaxV | по модели (ShipConfig) | потолок скорости; сток 330, линейка 305–485 (не жёсткий кламп — гравитация может разогнать сильнее) |
| LandSpeed | 55 | безопасная скорость касания (2026-10-03: было 38 — окно мягкой посадки шире) |
| TakeoffV | 85 | импульс взлёта |
| EngineMultiplier | 3.2 | множитель тяги у поверхности |
| LandingRingOffset | 90 | посадочное кольцо: r + 90 |
| CaptureRingK / Base | 3.3 / 30 | кольцо захвата (качель): r·3.3 + 30 |
| HeadingTurnRate | 4 1/с | скорость доворота носа к вектору скорости |
| HeadingMaxTurnSpeed | 260 град/с | предел угловой скорости доворота (2026-10-03) |
| MinControlSpeed | 1 | ниже — управление отключено |
| GravityBoost | 1.15 | буст «качель» |
| HpMax / FuelMax | по модели (ShipConfig) | сток 100 / 100; топливо в v0.1 не расходуется (задел `FuelDrainPerSecond = 5.5`) |

### Интегрирование и частота

Физика крутится в `FixedUpdate` — 50 Гц (`Fixed Timestep 0.02`). Схема —
**полуявный Эйлер**: сначала обновляется скорость (`v += a·dt`), потом позицию
интегрирует сам Rigidbody2D. Это стандартный и достаточный для игры метод;
орбиты устойчивы на дистанциях игры (у нас максимум ~10 000 юнитов и горизонты
прогноза единицы секунд).

Штатная гравитация Unity полностью выключена: `Ship.Init()` ставит
`Body.gravityScale = 0` — всё притяжение идёт только через `GravityField`.

### Две «космические» формулы (используются в игре и редакторе)

`PhysicsConfig` даёт честные формулы для круговой и второй космической скорости:

```csharp
public static float CircularVelocity(float g, float d) => Mathf.Sqrt(g / d);
public static float EscapeVelocity(float g, float d)   => Mathf.Sqrt(2f * g / d);
```

Это реальные формулы: v_круг = √(μ/d), v_уб = √(2μ/d), где μ — гравитационный
параметр. В игре `EscapeVelocity` — порог «качели» (ниже); в редакторе уровня по
ним считаются таблицы достижимости планет (`09_LEVEL_DESIGN.md` §2.4).

## 4. Физика полёта — управление

Всё управление — в `ShipController.FixedUpdate()` (`Scripts/Physics/ShipController.cs`).

### Модель: тяга вдоль вектора скорости

Управление «ракетное», но без ручного поворота: **нос корабля всегда сам
доворачивается к вектору скорости**, а тяга действует вдоль скорости:

```csharp
Vector2 dir = velocity / v;                       // курс = куда летим
if (thrustOn && v < shipConfig.MaxV)
    velocity += dir * (shipConfig.Thrust * engMul * dt);   // W — разгон
if (brakeOn) {
    float nv = Mathf.Max(0f, v - config.Retro * engMul * dt);
    velocity *= nv / v;                                // S — тормоз (по модулю)
}
```

- **W** — ускорение 95 ед/с² вдоль скорости (до потолка MaxV: сток 330, у линейки 305–485 из ShipConfig).
- **S** — уменьшение модуля скорости на 80 ед/с² (ретро-тормоз; у поверхности ×EngineMultiplier).
- Доворот носа — через физику (`Body.MoveRotation` с `HeadingTurnRate`), чтобы
  не конфликтовать с интерполяцией Rigidbody и не давать джиттер:

```csharp
float target = Mathf.Atan2(velocity.y, velocity.x) * Mathf.Rad2Deg - spriteNoseAngle;
float delta = Mathf.DeltaAngle(current, target);
// мягкий экспоненциальный доворот, но с пределом угловой скорости
float step = Mathf.Clamp(delta * HeadingTurnRate * dt,
                         -HeadingMaxTurnSpeed * dt, HeadingMaxTurnSpeed * dt);
ship.Body.MoveRotation(current + step);
```

Два предохранителя от «щёлкающего» носа (2026-10-03):

- **Предел 260 град/с** — без него экспонента при большом рассогласовании
  разгонялась до ~700 град/с: у нуля скорости вектор скорости разворачивается
  мгновенно, и нос «дёргался» вслед за ним.
- **Ниже 30 ед/с нос не доворачивается вовсе** (кроме финального захода) —
  направление околонулевой скорости это шум гравитации, а не намерение
  игрока. Держим последнюю осмысленную ориентацию.

`spriteNoseAngle = 90` в `Ship.prefab` — спрайт корабля нарисован носом вверх,
поле компенсирует это (0° носа = «вправо»).

### Боковая тяга A/D — фирменная механика

A/D дают ускорение **перпендикулярно** скорости — траектория изгибается, модуль
скорости почти не растёт («летать стало интересно» — главная находка прототипа):

```csharp
Vector2 perp = new Vector2(dir.y, -dir.x);                 // перпендикуляр к курсу
float maxTurn = config.StrafeMaxTurnRate * Mathf.Deg2Rad;  // 60°/с в радианы
float strafeAcc = Mathf.Min(config.StrafeAcc, v * maxTurn);
velocity += perp * (strafe * strafeAcc * engMul * dt);
```

**Ограничение `Min(StrafeAcc, v·ω_max)`** — из физики вращения: чтобы поворачивать
вектор скорости со скоростью ω, перпендикулярное ускорение нужно a⊥ = v·ω.
Без клампа медленный корабль крутился бы «как юла» (стрейф на месте разворачивал
вектор мгновенно). Знак перпендикуляра «перевёрнут» относительно прототипа — в
canvas HTML Y направлен вниз, в Unity вверх (это чинилось отдельным коммитом).

### «Качель» (гравитационный разгон)

```csharp
if (!wasInside && v > PhysicsConfig.EscapeVelocity(config.GravParamOf(body), d)) {
    velocity *= config.GravityBoost;   // ×1.15
}
insideRing.Add(body);
```

При **входе** в кольцо захвата тела (r·3.3 + 30) со скоростью выше убегающей —
единоразовый буст ×1.15. Вышел из кольца и вошёл снова — можно получить ещё раз.
Подробный разбор реализма — раздел 5.

### Посадочный режим

```csharp
if (planet != null && planetDist < planet.LandingRing)   // ближе r + 90
    engMul = config.EngineMultiplier;                    // ×3.2 ко всем тягам
```

У поверхности планеты все двигатели в 3.2 раза сильнее — «точный режим» для
посадки. Отслеживается ближайшая планета (не звезда).

### Взлёт

Обрабатывается в `Update()` (нажатие клавиши), сама логика в
`LandingSystem.Takeoff()`:

```csharp
Vector2 dir = (pos - planetPos).normalized;
ship.Body.linearVelocity = dir * ship.Config.TakeoffV;   // 85 от центра
```

## 5. Физика полёта — реализм: что честно, а что условно

Честный ответ на вопрос «у вас настоящая физика?» — **каркас ньютоновский,
числовые допущения — игровые**. Разбор по пунктам:

### Сделано как в реальности

| Что                      | Как в жизни                                                                                                                                                 |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Форма закона тяготения   | Ускорение ∝ 1/d² от каждого тела — закон обратных квадратов Ньютона                                                                                         |
| Суперпозиция             | Поле = векторная сумма вкладов всех тел одновременно (принцип суперпозиции)                                                                                 |
| Направление              | Притяжение всегда к центру тела (центральные силы)                                                                                                          |
| Сохранение движения      | Двигатель выключен — скорость не гасится сама (1-й закон Ньютона, вакуум без сопротивления). Штатная гравитация и демпфинг Rigidbody отключены              |
| Формулы орбит            | v_круг = √(μ/d), v_уб = √(2μ/d) — настоящие формулы, по ним считаются пороги и таблицы редактора                                                            |
| Эффект Оберта (частично) | Тяга у перицентра орбиты даёт больше энергии, чем на апоцентре — в нашей модели проявляется естественно, потому что тяга честно интегрируется с гравитацией |
| Прогноз траектории       | Численное интегрирование той же модели — так делаются прогнозы в «Kerbal Space Program»                                                                     |
| Отскок                   | Отражение нормальной составляющей скорости с коэффициентом восстановления: v′ = v − (1+e)·(v·n)·n — учебная формула удара, у нас e = 0.7                    |

### Игровые допущения (и зачем они)

| Что                       | Реальность                                                                                                             | У нас                                                                                                           | Зачем                                                                                                                                                   |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Масса тел                 | M в килограммах, своя у каждого тела                                                                                   | масса ∝ радиусу (μ = K·r·mult)                                                                                  | одна константа K задаёт всю систему; реальная масса ~ r³ потребовала бы раздельных плотностей и баланса ради каждого тела                               |
| Гравитационная постоянная | G = 6.674·10⁻¹¹                                                                                                        | K = 52 000 (юниты³/(масса·с²) — условные)                                                                       | игра оперирует «юнитами прототипа» (1 юнит ≈ 1 пиксель), реальные метры/кг не нужны                                                                     |
| Кламп ускорения 240       | У поверхности ускорение конечно, но у нас при малых d взлетает до тысяч                                                | a = min(μ/d², 240)                                                                                              | посадка: тяга 95 (×3.2=304 у поверхности) обязана пересиливать гравитацию, иначе посадка невозможна; кламп гарантирует управляемость                    |
| Движение тел              | Все тела притягивают друг друга (задача N тел)                                                                         | тела неподвижны, движется только корабль                                                                        | корабль — «пробная частица» (m корабля ≪ m планеты — так и в реальности спутники не сдвигают планеты); а вот планеты друг друга в реальности двигали бы |
| «Качель» ×1.15            | Гравитационный манёвр — обмен импульсом с **движущимся** телом; у неподвижной планеты разгона «ниоткуда» быть не может | тела неподвижны, поэтому честный манёвр невозможен — буст даётся бонусом при входе в кольцо со скоростью > v_уб | награда за смелые пролёты рядом с массивными телами; при этом эффект «разгоняйся у перицентра» (Оберт) в игре всё равно работает честно                 |
| Жар звезды                | Поток излучения ∝ 1/r²                                                                                                 | линейный: 0 на краю зоны → 30 HP/с у поверхности                                                                | линейный градиент читаемее игроку: понятно, что чем глубже — тем хуже                                                                                   |

## 6. Посадка и столкновения

Где: `Scripts/Physics/LandingSystem.cs` — компонент на корабле, событие `OnCollisionEnter2D`.

```csharp
float v = collision.relativeVelocity.magnitude;
if (star != null)  { Hull.ApplyDamage(ship.Hp); return; }   // звезда = смерть
if (v < ship.Config.LandSpeed) Land(planet, collision);   // < 55 — мягко
else                            Crash(planet, collision, v); // иначе — удар
```

### Посадка (`Land`)

- Снап на поверхность: `pos = центр + normal · (r + 7)`, скорость в ноль,
  нос разворачивается по нормали (стоит «вертикально»).
- `ship.LandedOn = planet; ship.State = Landed;` — ввод полёта отключается,
  W = взлёт.
- **Станция обслуживает любую посадку, на которой корабль уцелел** (правило
  2026-10-03; ремонт — строго через `HullSystem.RepairAll()`: он стреляет
  `HpChanged`, иначе HUD зависает на старой цифре — баг плейтеста 2026-10-03): смерть есть смерть — смертельный удар гибелит через HullSystem до
  всякого сервиса; выжившему — даже с 1% корпуса — бак и HP до 100%. Порог
  мягкой посадки поднят 38 → 55 (окно мягкого касания шире, меньше случайных
  повреждений).

### Удар (`Crash`)

```csharp
float damage = Mathf.Max(5f, (v - ship.Config.LandSpeed) * 0.9f);
Hull.ApplyDamage(damage);
CameraFollow.AddShake(Mathf.Clamp01(damage / 45f) * 0.7f); // толчок камеры по урону
if (ship.Hp > 0f) Land(planet, collision); // выжил — считай сел
```

- Урон = (v − 38) · 0.9, минимум 5 — при 100 HP смерть примерно на скорости 148.
- Отскоков нет: выживший удар сразу считается посадкой — корабль не дребезжит
  о поверхность (раньше был отскок с e=0.7 — убран как мешающий).
- Толчок камеры пропорционален урону — «въехал» чувствуется и глазами.

### Липкая посадочная ориентация (2026-10-03)

`ShipController.retroAttitude` — конечный автомат вместо «режим = зажатая S»:

- **Вход**: тормоз (S) внутри посадочного кольца, не финальный заход — корабль
  разворачивается двигателями по движению (как Falcon на посадке).
- **Держится**: S отпущен — ориентация остаётся, нос не скачет туда-сюда
  посреди снижения. Камера остаётся в посадочном зуме.
- **Выход**: посадка / выход из кольца / тяга (W — «улетаем»).

Явную клавишу-переключатель обсудили и отвергли: лишнее нажатие каждые
30–60 с цикла и риск «забыл выключить». Ориентация с гистерезисом — как
flight assist в X4/Elite.

Взлёт: `Takeoff()` — импульс 85 от центра планеты (раздел 4).

## 7. Звёзды, жар, гибель и респавн

### Жар — `HullSystem.ApplyHeat()` (FixedUpdate корабля)

```csharp
float k = Mathf.Clamp01(1f - (d - star.Radius) / (star.HeatRadius - star.Radius));
ApplyDamage(k * star.HeatDamagePerSecond * dt);
```

Внутри жаровой зоны (радиус `HeatRadius`, у звёзд по умолчанию 3.6·r) урон
нарастает линейно от 0 на краю до 30 HP/с у поверхности. Визуальная заглушка
зоны — полупрозрачный оранжевый круг (`WorldBuilder.CreateBody`, sortingOrder −1).
Касание самой звезды — мгновенная гибель (`LandingSystem.OnCollisionEnter2D`).

### Гибель и респавн — `HullSystem.Die()` / `RespawnAfter()`

- `Hp` падает до 0 → событие `Died`, `State = Respawning`, пауза 0.6 с
  (корутин, место под взрыв).
- Респавн: телепорт на поверхность **планеты старта** (`StartPlanetIndex` уровня,
  угол `SpawnAngleDeg`), скорость 0, HP полный, `State = Landed` — стоим на планете,
  как в начале игры.
- События `HpChanged/Died/Respawned` — задел под HUD/звуки (слушателей в v0.1 нет).

## 8. Прогноз траектории (пунктир)

Где: `Scripts/Physics/TrajectoryPredictor.cs` (компонент на корабле).

- Симулирует **ту же формулу гравитации** (`GravityField.GetAccelerationAt`) без
  тяги: шаг 1/120 с (мельче игрового — точнее).
- Горизонт **адаптивный**: ~1.2 экрана вперёд, от 2 до 4 секунд, сглажен 4/с;
  опорная ширина экрана фиксирована на сессию — живой зум (320–470) менял её
  и конец линии «дёргался». Короткий горизонт ещё и убирает хлёст конца:
  чувствительность к начальным условиям растёт как время². Затухание к концу
  (endFade 0.8) прячет остаточный шум дальнего хвоста (2026-10-03).
- Линия — пул чёрточек-спрайтов (до 64), шаг пунктира адаптивный: если горизонт
  не влезает в пул, интервал растёт (`spacingNow = max(spacing, v·horizon/N)`).
- Обрыв при столкновении: проверка пересечения с радиусом каждого тела (r+4).
  При касании планеты с прогнозируемой скоростью ниже порога посадки вся линия
  **зелёная** — «сейчас сядешь мягко». Красной линии сознательно нет (2026-10-03):
  к планете летишь почти всегда, красное краснело бы непрерывно — шум.
  Опасность показывают цифра и красный цвет скорости в посадочном кольце.
- Стартует из носа (`noseOffset 6`), направлена по носу, длина = фактическая
  скорость — на медленной скорости чёрточки сжимаются у носа, на быстрой —
  длинная линия.
- Прячется при посадке и скорости < 0.5 ед/с.

Это «бесплатный» честный прогноз: одна и та же физика для игры и предсказания,
никакого специального математического аппарата (конические сечения и т.п.) не нужно.

## 9. Мир: данные уровня и сборка сцены

### LevelAsset (`Scripts/World/LevelAsset.cs`, ScriptableObject)

```csharp
public sealed class LevelAsset : ScriptableObject {
    public string LevelName;
    public List<CelestialBodyData> Bodies;      // тела уровня
    public SpawnMode SpawnMode;                 // Landed (v0.1) / Free (задел)
    public int StartPlanetIndex;                // планета старта = точка респавна
    public float SpawnAngleDeg;                 // точка на поверхности: 0=восток, 90=север
}
public sealed class CelestialBodyData {
    public string DisplayName; public BodyType Type;   // Planet/Star (+BlackHole и др. — задел)
    public Vector2 Position; public float Radius; public float MassMultiplier;
    public float HeatRadius;                  // только звёзды
    public BodyVisuals Visuals;               // спрайт/материал/цвет/вращение
    public float LandingRingRadius, CaptureRingRadius; // 0 = считать по формуле
}
```

Уровень — чистые данные: правится в инспекторе или редактором уровня, игра
строит мир из них при каждом старте. **Balance-параметры** (тяга, гравитация,
кольца) — в отдельном `PhysicsConfig` (ScriptableObject): баланс правится без кода.

### CelestialBody → Planet / Star (`Scripts/World/`)

- `CelestialBody.Init(data, config)`: переносит данные, масштабирует спрайт префаба
  под радиус (`визуальный диаметр = 2·Radius`), подгоняет CircleCollider2D
  (`radius = Radius / scale` — коллайдер в локальных единицах), запоминает кольца.
- `OnEnable/OnDisable` — саморегистрация в `GravityField` (поэтому он создаётся первым).
- Свойства `LandingRing` (r+90) и `CaptureRing` (r·3.3+30) — с override-ами из данных.
- `Planet` — пустой наследник (посадочная логика в LandingSystem корабля);
  `Star` — добавляет `HeatRadius`, `HeatDamagePerSecond = 30`, `IsInHeatZone()`.
- `Update` — медленное вращение спрайта (`SpinSpeed`), коллайдер круглый — не меняется.

### Префабы — источник визуала

`Planet.prefab` и `Ship.prefab` (в Git был отдельный коммит «Prefabs are the source
of truth for visuals»): спрайт/цвет планет и корабля задаются в префабах руками,
`WorldBuilder` инстанцирует их и применяет override-ы из данных. Фолбэк без
префаба — генерация заглушек кодом (раздел 16).

## 10. Камера

`Scripts/Physics/CameraFollow.cs` — ортографическая, следует за кораблём:

```csharp
pos.x += (target.x - pos.x) * Mathf.Min(1f, 3.5f * dt);   // лерп позиции 3.5/с
cam.orthographicSize += (targetSize - cam.orthographicSize) * Mathf.Min(1f, 3f * dt);
```

- **Опережение по курсу (lookahead):** камера смещается вперёд по вектору
  скорости (0.45 с полёта, максимум 130 юнитов, сглаживание 3/с) — видно,
  куда летишь, реакция не «в последний кадр». На стоянке смещение уходит в ноль.
- **Скоростной зум:** высота видимой области растёт от **320 юнитов** на малой
  скорости до **470** на максимальной (лерп по v/MaxV). Посадочный режим —
  по-прежнему **190** (планета «растёт»).
- **Дрожь от ударов (trauma-модель):** сила = trauma², спад 1.6/с, смещение —
  гладкий шум Перлина (не рваный рандом) до 15 юнитов + лёгкий наклон 2.5°.
  Толчки: касание 0.08, взлёт 0.25, удар ~0.35–0.7 (по урону), гибель 0.85.
  `CameraFollow.AnchorPosition` — позиция без дрожи: параллакс-фон держится
  за неё, поэтому тряска видна и на фоне.
- Лерп (линейная интерполяция с экспоненциальным сглаживанием) — камера не
  жёстко приколота, а «догоняет» — мягкое ощущение полёта.
- Высоту 320 знает редактор уровня (рамка «что видит игрок»).

## 10а. Ощущение полёта (game feel)

Итерация 2026-10-03: движение — главная механика, полёт должен «чувствоваться».
Четыре подсистемы отклика, все процедурные (без ассетов, в духе альфы).

**Параллакс-фон** — `Scripts/World/StarfieldParallax.cs` (на камере, добавляет
GameSession). Три слоя звёзд (90/60/36 шт., StubSprites-круги): слой стоит на якоре
камеры без дрожи (обязательно z=0 — якорь наследует z камеры −10, и слои
отсекались near-плоскостью, звёзд «не было видно»), звёзды дрейфуют внутри
тайла с долей скорости камеры — 0.12/0.35/0.65 — и заворачиваются по краям
(`% tile`): бесконечное поле без швов. Дальние — мельче и тусклее. Это
решает главную проблему ощущения скорости: между планетами корабль
больше не «висит».

**Скоростной шлейф** — `Scripts/Physics/SpeedTrail.cs` (на корабле, добавляет
WorldBuilder). TrailRenderer с тайлящимся круглым спрайтом: включается
выше 65 ед/с, толщина растёт с v/MaxV (0.5→2.6 юнита). Телепорты (посадка,
респавн) шлейф очищают, чтобы не тянулся через полкарты.

**Живые двигатели** — `Scripts/Physics/EngineEffects.cs` (на корабле).
Четыре процедурных ParticleSystem: выхлоп тяги из кормы (тёплый), ретро-сопла
из носа (холодный, в посадочном развороте сами разворачиваются «двигателями
вперёд»), боковые микросопла стрейфа. Состояние двигателей публикует
ShipController (`ThrustOn/BrakeOn/StrafeLevel/EnginePower`) — пустой бак
и посадочный множитель ×3.2 учтены: у поверхности пламя гуще и крупнее.

**Посадочная индикация** — в `HudBinder`: внутри посадочного кольца цифра
скорости зелёная (ниже порога посадки — касание будет мягким) или красная
(разобьёшься). Решение «тормозить или садиться» считывается без арифметики
в голове.

## 13. Звук

Архитектура закладывалась сразу (решение начала проекта) — `Scripts/Audio/`:

### AudioManager (`Scripts/Audio/AudioManager.cs`)

- Синглтон + `DontDestroyOnLoad`: создаётся в MainMenu, живёт во всех сценах;
  дубль самоуничтожается в `Awake`.
- **Каталог**: `AudioCatalog` (ScriptableObject) — соответствие «событие →
  клип(ы) + громкость/тон/группа». Замена звука = правка ассета, код не трогаем.
  `SoundId` — enum всех событий (14 + музыка).
- **Группы**: Engine / Sfx / UI / Music — раздельные громкости, хранятся в
  `PlayerPrefs` (`audio.vol.Master` и т.д.), переживают перезапуск.
- **One-shot**: пул до 12 голосов, перебиваем старейший при переполнении;
  вариации клипов (у столкновений 3 штуки) — по возрастанию силы (`Sequential`)

- **Лупы** (двигатель, жар): `SetLoopActive/SetLoopIntensity/SetLoopPan` —
  громкость/тон от интенсивности, стерео-панорама для стрейфа, фейды 0.15 с

- **Музыка**: два AudioSource (A/B) и кроссфейд 1.5 с — смена трека без тишины.
- **Ducking**: взрыв приглушает двигатели/эффеты до 20% и плавно возвращает за 1.2 с.
- Фасад `Sound.Play(...)` — статические вызовы из любого кода без ссылок.

## 18. Вопрос-ответ для защиты (FAQ)

**— Почему своя гравитация, а не встроенная Unity?**
Штатная гравитация 2D — один постоянный вектор на весь проект (для «платформеров»).
Нам нужно притяжение от N тел, зависящее от расстояния по закону 1/d². Поэтому
`gravityScale = 0` и своё суммарное ускорение в FixedUpdate (`GravityField.GetAccelerationAt`).

**— Почему FixedUpdate, а не Update?**
Физика требует постоянного шага (0.02 с): при переменном dt интегрирование Эйлера
«поплыло» бы — орбиты дрожали бы при просадках FPS. Update — для ввода и UI.

**— Почему Rigidbody2D, а не своя позиция?**
Collider2D/физический движок дают коллизии (посадка!), интерполяцию (плавная
картинка при 50 Гц физики), Continuous-детект (быстрый корабль не проскакивает
сквозь планету). Скорость мы считаем сами и присваиваем `linearVelocity`.

**— Насколько физика реалистична?**
Каркас — ньютоновский: 1/d², суперпозиция, сохранение скорости без тяги,
настоящие формулы v_круг/v_уб. Допущения — игровые: масса тел ∝ радиусу, кламп
ускорения 240 (управляемость посадки), тела неподвижны (задача N тел не решается),
«качель» ×1.15 — игровой бонус, т.к. у неподвижной планеты честный гравитационный
манёвр невозможен. Подробная таблица — раздел 5.

**— Как настраивается баланс без программиста?**
Все числа — в ScriptableObject (`PhysicsConfig`, `LevelAsset`, `AudioCatalog`):
правятся в инспекторе, код не пересобирается. Изменение гравитации ×2 (26000→52000)
после плейтеста — одна цифра в ассете.

**— Почему уровень — данные, а не сцена?**
Один `WorldBuilder` строит любой уровень из `LevelAsset`; редактор уровня пишет
в те же данные; смена уровня — смена одной ссылки. Плюс LevelAsset читается
редактором для гизмо и валидации.

**— Что даёт редактор уровня?**
Добавление/настройка тел мышью и полями, кольца/жар/спавн/дистанции/рамка камеры
в Scene View, drag со snap и Undo, живая валидация (7 проверок), зонд гравитации
(Ctrl), поле стрелок и прогноз траектории спавна. Сборка уровня «5 планет + звезда»
— ~10 минут.

**— Как прогноз траектории угадывает путь?**
Он не угадывает — интегрирует ту же самую модель физики вперёд (шаг 1/120 с,
горизонт 4 с) и обрывается о поверхность тела. Идентичность формул гарантирует
совпадение с реальным полётом.

**— Как посажен звук?**
Центральный AudioManager-синглтон (переживает сцены) + каталог «событие→клип»
(ScriptableObject) + группы громкости в PlayerPrefs. Лупы с интенсивностью и
панорамой, кроссфейд музыки, ducking при взрыве. В v0.1 SFX временно отключены —
вся проводка на месте.

**— Как обрабатывается одновременное ESC у карты и паузы?**
Флаг `EscJustClosed` на один кадр: ESC закрывает карту, пауза проверяет флаг и в
этом кадре не включается (`MapScreenController.LateUpdate` сбрасывает).

**— Что дальше после прототипа?**
Подключение хвостов (сейвы, HUD-данные), SFX, затем этапы полной игры: заказы и
пассажиры → экономика → финальный маршрут (`07_ROADMAP.md`).

## 20. Банк развёрнутых ответов: «как это работает?»

Готовые реплики для защиты. Схема ответа: **одна фраза сути → где в коде →
детали, если спросят**. Значок 📁 — что открыть и показать.

### 20.1 Движение и полёт

**— Как работает движение корабля? Покажи.**
Полный цикл такой: игрок жмёт W → Input System (ассет `GameInput`, карта Ship,
действие Thrust) → в `ShipController.FixedUpdate` я читаю `thrustAction.IsPressed()`,
беру текущую скорость с Rigidbody2D, прибавляю к ней ускорения — гравитацию от
`GravityField`, потом тягу/тормоз/стрейф — и записываю скорость обратно
`ship.Body.linearVelocity = velocity`. Позицию интегрирует сам физический движок
Unity из этой скорости. Всё в FixedUpdate, 50 раз в секунду, с фиксированным
шагом — чтобы физика не зависела от FPS.
📁 `ShipController.cs` → метод `FixedUpdate` (весь метод читается сверху вниз:
гравитация → качель → посадочный режим → тяга/тормоз/стрейф → запись скорости →
доворот носа).

**— Почему корабль поворачивается сам? Я не управляю направлением.**
Управление «ракетно-такси»: игрок управляет не поворотом, а траекторией. Нос
корабля плавно доворачивается к вектору скорости — как флюгер: корабль летит
туда, куда его несёт. Реализовано через `Body.MoveRotation` с параметром
`HeadingTurnRate = 4` (экспоненциальное сглаживание, поворот за ~0.25 с).
Поворот сделан через физический API, а не через `transform.rotation`, иначе
он конфликтует с интерполяцией Rigidbody и картинка дрожит — это был реальный
баг, чинил отдельным коммитом.
📁 `ShipController.cs` → конец `FixedUpdate` (блок «Нос доворачивается»).

**— Как работает боковая тяга A/D? Почему скорость от неё не растёт?**
A/D дают ускорение строго перпендикулярно вектору скорости: беру направление
полёта `dir`, перпендикуляр — `(dir.y, -dir.x)`. Перпендикулярное ускорение
изменяет направление вектора, почти не меняя его длину — это геометрия:
приращение ⊥ скорости поворачивает вектор. Поэтому траектория изгибается,
а скорость не растёт. Есть защита от «юлы»: перпендикулярное ускорение нужно
a = v·ω, поэтому оно ограничено `Min(StrafeAcc, v · 60°/с)` — медленный корабль
физически не может развернуться мгновенно.
📁 `ShipController.cs` → блок стрейфа в `FixedUpdate` (там комментарий про
знак перпендикуляра: в HTML-canvas Y вниз, в Unity вверх).

**— Что такое «качель»?**
Награда за смелый пролёт у массивного тела. У каждого тела есть «кольцо захвата»
радиусом r·3.3 + 30. Если корабль ВХОДИТ в это кольцо со скоростью выше убегающей
(по честной формуле v = √(2μ/d)), вся его скорость умножается на 1.15 —
один раз за вход. Реализовано множеством `insideRing`: запоминаем, в каких
кольцах уже были, повторно буст не даём, пока не выйдем.
📁 `ShipController.cs` → цикл `foreach (CelestialBody body in gravity.Bodies)`.

**— Почему с выключенным двигателем корабль летит и не останавливается?**
Потому что в космосе нет сопротивления среды, а мы его честно не придумываем:
гравитация проекта отключена (`gravityScale = 0` в `Ship.Init`), демпфирование
Rigidbody равно нулю, и каждый кадр мы сами пересчитываем скорость только из
гравитации и тяги. Нет тяги — меняет скорость только гравитация. Это первый
закон Ньютона.
📁 `Ship.cs` → `Init` (строка `Body.gravityScale = 0f`).

**— Как ограничена максимальная скорость?**
Никак «жёстко» — ограничена работа двигателя: условие тяги `if (thrustOn && v < MaxV)`.
Выше 330 двигатель просто не помогает, но гравитация, например, при падении
к звезде может разогнать и сильнее — кламп именно на управляемую тягу, не на
физику. Это осознанное решение для читаемости.
📁 `ShipController.cs` → строка с `v < shipConfig.MaxV`.

**— Как работает взлёт с планеты?**
Корабль стоит на планете (состояние `Landed`), полётный ввод отключён.
Нажатие W ловится в `Update` (не в FixedUpdate — нажатия «в один кадр» между
физическими шагами теряются), вызывается `LandingSystem.Takeoff()`: скорость
= направление от центра планеты × 85, состояние → Flying.
📁 `LandingSystem.cs` → `Takeoff`; вызов — `ShipController.Update`.

### 20.2 Гравитация и орбиты

**— Как реализована гравитация? Покажи формулу.**
Свой класс `GravityField` — реестр всех тел сцены + одна функция
`GetAccelerationAt(позиция)`: для каждого тела считаю вектор до него, ускорение
по закону обратных квадратов a = μ/d² с потолком 240, и векторно складываю
вклады всех тел. μ тела = 52000 · радиус · множитель массы (у планет 1,
у звёзд 4.5). Тела сами регистрируются в поле при появлении (`OnEnable`).
📁 `GravityField.cs` → `GetAccelerationAt` (10 строк, можно показать целиком).

**— Почему своя гравитация, а не встроенная Unity?**
Встроенная 2D-гравитация Unity — это один постоянный вектор для всего проекта
(для платформеров). А мне нужно притяжение от N тел, зависящее от расстояния,
с суммированием. Поэтому штатная выключена, и своя считается в FixedUpdate.

**— Почему гравитация в FixedUpdate?**
Интегрирование Эйлера требует постоянного шага. В Update шаг плавает с FPS —
орбиты дрожали бы при просадках. FixedUpdate — фиксированные 0.02 с.

**— Какие настоящие физические формулы используются?**
Три. Закон тяготения (1/d²) — сама гравитация; круговая скорость v = √(μ/d) и
вторая космическая v = √(2μ/d) — статические методы `PhysicsConfig.CircularVelocity`
и `EscapeVelocity`, используются как порог качели и в редакторе уровня для
таблиц достижимости планет (посадка возможна, если тяга в кольце 304 > v_круг).
📁 `PhysicsConfig.cs` → два статических метода внизу файла.

**— Зачем ограничение ускорения 240?**
Без него у поверхности тела ускорение по 1/d² взлетает до тысяч (у Гавани на
поверхности было бы 2000). Тяга корабля 95 (×3.2 у поверхности = 304) обязана
пересиливать гравитацию, иначе взлёт и посадка неуправляемы. Потолок 240 < 304 —
гарантия управляемости. Числа подобраны так, чтобы посадка была честно трудной,
но возможной на любой планете уровня.

**— Планеты двигаются? Друг друга притягивают?**
Нет, тела неподвижны — корабль «пробная частица» (как спутник возле планеты:
он падает на неё, а она на него — незаметно). Полная задача N тел (все тела
друг на друге) в игре не решается — это и не нужно для геймплея, а вот астероиды
и кометы, которые будут двигаться, — следующие этапы.

**— Насколько это реалистично вообще?**
Каркас ньютоновский: 1/d², суперпозиция, сохранение скорости, реальные формулы
переходных скоростей, даже эффект Оберта работает (тяга у перицентра даёт
больше энергии). Допущения игровые: масса ∝ радиусу, кламп, статичные тела,
буст качели (у неподвижной планеты честный гравитационный манёвр невозможен —
там нужен обмен импульсом с движущимся телом). Полная таблица «реальность vs
игра» с обоснованием каждого допущения — раздел 5 этого документа.

### 20.3 Посадка, урон, гибель

**— Как игра понимает: посадка это или авария?**
Физический движок даёт коллизию `OnCollisionEnter2D`. Я беру
`collision.relativeVelocity.magnitude` — скорость контакта. Меньше 55 — посадка
(снап на поверхность, скорость в ноль, состояние Landed). Больше — удар.
📁 `LandingSystem.cs` → `OnCollisionEnter2D` (весь if/else — 5 строк).

**— Как считается урон при столкновении?**
Урон = (скорость − 55) · 0.9, минимум 5. При 100 HP гибель на скорости
примерно 148. Формула из HTML-прототипа, сохранена для единства ощущений.

**— Как работает отскок?**
Учебная формула удара с коэффициентом восстановления e = 0.7: раскладываю
скорость на нормальную и касательную к поверхности, нормальную отражаю с
множителем (1+e) = 1.7 — это `velocity -= 1.7f * vd * normal` — и дополнительно
гашу всё до 45% (неупругий удар: часть энергии уходит в «деформацию корпуса»).
Плюс выталкивание над поверхностью, чтобы коллайдеры не слипались.
📁 `LandingSystem.cs` → `Crash`.

**— Как работает жар звезды?**
У звезды есть радиус жаровой зоны (по умолчанию 3.6·r, у тестовой Печи 180).
Внутри зоны каждый физический шаг `HullSystem.ApplyHeat`: доля близости k от 0
на краю до 1 у поверхности, урон = k · 30 HP/с. Линейный градиент вместо
реального 1/r² — сознательно: игроку понятно «глубже = хуже». Касание самой
звезды — мгновенная гибель.
📁 `HullSystem.cs` → `ApplyHeat`; `Star.cs` → `IsInHeatZone`.

**— Что происходит при прочности 0?**
`HullSystem.Die()`: событие Died, состояние Respawning, пауза 0.6 с корутиной
(место под взрыв) → телепорт на планету старта уровня (индекс и угол из
LevelAsset), скорость 0, HP полный, состояние Landed — как в начале игры.
События HpChanged/Died/Respawned — задел под HUD и звук.
📁 `HullSystem.cs` → `Die`, `RespawnAfter`.

**— Как работает пунктирный прогноз? Почему он сбывается?**
Он не «предсказывает» — он ЗАРАНЕЕ ПРОЖИВАЕТ ту же физику: та же функция
`GravityField.GetAccelerationAt`, тяги нет, шаг мельче (1/120 с), горизонт 4 с.
Формулы идентичны → линия совпадает с будущим полётом. Обрывается о поверхность
любого тела (проверка пересечения). Так же устроены прогнозы в Kerbal Space
Program. Чёрточки — пул из 64 спрайтов, переиспользуемых каждый кадр, без
создания объектов — нет мусора для сборщика.
📁 `TrajectoryPredictor.cs` → `Simulate`.

### 20.4 Архитектура и данные

**— Почему уровни — ScriptableObject, а не объекты в сцене?**
Уровень — это ДАННЫЕ: список тел (тип, позиция, радиус, масса, жар), точка
старта. Храню в `LevelAsset` (ScriptableObject). При старте `WorldBuilder`
строит из данных живые объекты. Выгоды: один код строит любой уровень; редактор
уровня пишет в те же данные; смена уровня — смена одной ссылки в инспекторе;
данные можно сравнивать скриптами (валидация). Сцена при этом почти пустая.
📁 `LevelAsset.cs` (классы данных), `WorldBuilder.cs` → `Build`.

**— Как мир собирается при старте?**
`GameSession.Start()` создаёт `WorldBuilder` и вызывает `Build()`: сначала
GameObject с `GravityField` (реестр должен существовать ДО тел), потом в цикле
каждое тело из LevelAsset — инстанс префаба Planet (звезда — кодом),
`CelestialBody.Init` подгоняет масштаб спрайта и коллайдер под радиус, тело при
включении само регистрируется в поле. Последним — корабль: инстанс `Ship.prefab`
на поверхность планеты старта, состояние Landed. Потом вешается CameraFollow.
📁 `GameSession.cs` → `Start` (весь метод — 6 строк).

**— Что висит на корабле? Почему так много компонентов?**
`Ship.prefab` = конструктор из независимых систем: Rigidbody2D + CircleCollider2D
(физика/коллизии), `Ship` (состояние: Flying/Landed, HP, топливо), `ShipController`
(ввод и полёт), `LandingSystem` (контакты), `HullSystem` (урон/респавн),
`TrajectoryPredictor` (пунктир), `ShipAudio`/`HeatAudio` (звук). Каждый отвечает
за одно — можно снять любой, остальное работает. Это композиция вместо
одного «бог-класса».
📁 `WorldBuilder.cs` → `CreateShip` (fallback-ветка собирает те же компоненты кодом).

**— Как правится баланс без программиста?**
Все числа вынесены в ассеты: `PhysicsConfig` (тяга, гравитация, кольца),
`LevelAsset` (тела), `AudioCatalog` (звук). Пример из жизни: после плейтеста
гравитация показалась слабой — умножил одну цифру в ассете (26000 → 52000),
код не пересобирался. Тяга боковая 85 → 130 — тоже правка ассета.
📁 `PhysicsConfig_Default.asset` в инспекторе.

**— Что за SpaceTaxi.Gameplay.asmdef?**
Описание сборки C#: все игровые скрипты компилируются в отдельную библиотеку
SpaceTaxi.Gameplay (не в общий Assembly-CSharp). Компиляция быстрее и границы
чёткие: Editor-инструменты не видят игровую логику и наоборот.

**— Как добавить в игру новую планету?**
Три способа: 1) в редакторе уровня — кнопка «+ Планета», поставить мышью,
сохранить (Ctrl+S); 2) в инспекторе LevelAsset — дописать элемент списка;
3) кодом — в BigMap01 карту генерировал отдельный python-скрипт с проверками.
Игра при следующем запуске сама построит новую планету.

**— Как тестировался проект?**
Три контура: 1) автопроверки компиляции и сцены через Unity CLI (официальный
`unity` CLI + пакет com.unity.pipeline — агент выполнял C# прямо в редакторе);
2) плейтесты по сценариям (взлёт → посадки по нарастающей → жар → респавн,
сценарий в `09_LEVEL_DESIGN.md` §2.6); 3) git-история — каждая правка отдельным
коммитом с описанием (лаг редактора, джиттер камеры, инвертированный стрейф —
все фиксы видны). Тестовых сценариев Unity Test Framework в v0.1 нет — физика
проверялась плейтестами и таблицами редактора.

### 20.5 Интерфейс

**— Как устроен UI технически?**
Один Canvas (Screen Space Overlay, CanvasScaler 1920×1080) на сцену, всё UI —
обычные объекты сцены, стилизация компонентами (цвета, TMP-шрифт JetBrains
Mono). Скриптов минимум — только поведение: панель, карта, пауза, настройки,
переходы. Стиль — «ретро-зелёный терминал»: прямоугольные панели, монохром,
жёлтый акцент такси.
📁 сцена `GameScene.unity`, объект `UI_Root` (7 поддеревьев).

**— Как работает выезжающая панель бортового компьютера?**
`OnboardComputerPanel`: панель — RectTransform шириной 480. При TAB — корутина
`Slide`: за 0.25 с интерполирую anchoredPosition.x от −510 (за экраном) до 0 по
кривой ease-out cubic (быстро выезжает, плавно докатывается). На unscaled-времени,
чтобы работала и на паузе.
📁 `OnboardComputerPanel.cs` → `Toggle`, `Slide`.

**— Как решён конфликт: ESC должен и паузу ставить, и карту закрывать?**
«Кадровый guard»: ESC при открытой карте закрывает её и ставит флаг
`EscJustClosed = true` до конца кадра. Пауза в своём Update видит флаг и в этом
кадре не включается. В LateUpdate флаг сбрасывается. Итого одно нажатие ESC —
ровно одно действие.
📁 `MapScreenController.cs` → `Update`/`LateUpdate`; `PauseScreenController.cs` → `Update`.

**— Как сделана пауза?**
`Time.timeScale = 0` — останавливается игровое время (физика, корутины на
игровом времени), UI работает. Одновременно показываются: затемнение, бортовой
компьютер слева, меню паузы справа. Анимации UI на unscaledDeltaTime — поэтому
панель может выезжать прямо на паузе.
📁 `PauseScreenController.cs` → `SetPaused`.

**— Как переходят между сценами?**
`SceneManager.LoadScene("GameScene")` из кнопок меню (`SceneFlowButtons`).
AudioManager при этом НЕ умирает — он с `DontDestroyOnLoad`, музыка играет
сквозь переход; его дубль в новой сцене видит живой Instance и самоуничтожается
в Awake. «Выход» в редакторе останавливает Play Mode (`#if UNITY_EDITOR`), в
билде — `Application.Quit()`.

**— Как в меню кнопка «Продолжить» понимает, есть ли сохранение?**
В v0.1 — упрощение: сохранений нет, кнопка всегда выключена (в доке дизайна
решение: не затемнять, а убирать). Настоящий SaveSystem — следующий этап,
его проект уже описан (позиция/скорость/HP/топливо/уровень в JSON).
📁 `SceneFlowButtons.cs` → `ContinueGame` (там честный комментарий).

### 20.6 Звук

**— Как устроена звуковая подсистема?**
Центральный `AudioManager`-синглтон + каталог `AudioCatalog` (ScriptableObject):
«событие → клип(ы) + громкость/тон/группа». Код зовёт `Sound.Play(SoundId.Takeoff)` —
статический фасад, никаких ссылок. Замена звука = правка ассета, код не трогаем.
📁 `AudioManager.cs` (класс + фасад `Sound` внизу файла), `AudioCatalog.cs`.

**— Как играется музыка при смене сцен?**
AudioManager создаётся в MainMenu с `DontDestroyOnLoad` и живёт всю игру.
В каждой сцене объект `SceneMusic` говорит, ЧЕМУ играть: меню → MusicMenu,
полёт → MusicFlight. Смена трека — кроссфейд 1.5 с на двух AudioSource (A/B
чередуются) — без тишины на стыке.
📁 `SceneMusic.cs` (весь файл — 30 строк), `AudioManager.PlayMusic`/`Crossfade`.

**— Что умеет система звука сверх «играть файл»?**
Непрерывные лупы с управляемой громкостью/тоном/стерео-панорамой (двигатель
громче при тяге, стрейф слева/справа); вариации клипов (3 удара по силе);
группы громкости (двигатели/эффекты/UI/музыка) с сохранением в PlayerPrefs;
«приглушение» (ducking) — взрыв срезает остальные звуки на 1.2 с; пул one-shot
на 12 голосов с перебиванием старейшего.
📁 `AudioManager.cs` → `SetLoopIntensity`, `DuckAll`, `GetFreeOneShotVoice`.

**— Почему в демо звук только музыкальный?**
Систему закончили, но SFX корабля (двигатель, удары, жар) временно отключили
решением от 20.09 — на плейтесте мешали, финальные клипы подбираются отдельно.
Вызовы в `ShipAudio`/`HeatAudio` закомментированы с пометкой, включение —
раскомментировать три блока, вся проводка готова.
📁 `ShipAudio.cs` → `Update` (комментарий «ЗВУК ВЫКЛ»).

### 20.7 Редактор уровня

**— Как работает редактор уровня? Из чего состоит?**
Два файла. `LevelEditorWindow` — окно (меню Space Taxi → Level Editor): выбор
LevelAsset, список тел, панель параметров выбранного тела, блок спавна, живая
валидация. `LevelEditorSceneView` — рисование в Scene View: кольца, жар, спавн,
дистанции. Окно и сцена общаются через статику (окно хранит выбранный уровень
и индекс, SceneView их читает).
📁 `Editor/LevelEditorWindow.cs`, `Editor/LevelEditorSceneView.cs`.

**— Как правки сохраняются? Почему нет кнопки «Сохранить»?**
Работаю через `SerializedObject`/`SerializedProperty` — тот же механизм, что у
инспектора Unity: `so.ApplyModifiedProperties()` пишет в ассет и регистрирует
Undo; на диск — стандартный Ctrl+S. Это лучший UX: меньше кнопок — меньше
ошибок. Грубые правки (drag) дополнительно оборачиваю `Undo.RecordObject`.

**— Как сделано перетаскивание тел мышью в Scene View?**
В `OnSceneGui` ловлю события мыши: MouseDown — ищу тело под курсором (расстояние
до центра < радиуса), запоминаю смещение и делаю `Undo.RecordObject`;
MouseDrag — новая позиция = курсор + смещение, при включённом snap округляю
до 10 (Shift — свободно), `EditorUtility.SetDirty`; MouseUp — конец. Плюс
стрелки клавиатуры (1 юнит, Shift — 10). Во время drag рядом с телом печатаются
координаты.
📁 `LevelEditorSceneView.cs` → `HandleDrag` (60 строк — вся логика).

**— Что за кольца и подсказки рисуются в сцене?**
Через Handles API: посадочное кольцо (r+90) — зелёный пунктир; кольцо качели
(r·3.3+30) — голубой точечный; жар звезды — оранжевый пунктир с заливкой; от
выбранного тела — линии дистанций до всех остальных с числами (ближе 300 —
красным: опасная теснота); маркер спавна (треугольник + стрелка курса) и рамка
«что видит игрок» (320×569 — реальные размеры игровой камеры). Плюс опционально:
прогноз траектории после взлёта и поле стрелок гравитации.
📁 `LevelEditorSceneView.cs` → `DrawBody`, `DrawSelectionDistances`, `DrawSpawn`.

**— Что показывает «зонд гравитации»?**
Зажимаешь Ctrl — в точке курсора рисуется стрелка суммарного притяжения всех
тел и его величина в ед/с², цвет от синего к красному. Формула — та же, что в
игре (`GravityAt` — копия `GravityField.GetAccelerationAt` без MonoBehaviour).
Это инструмент левел-дизайнера: «куда понесёт корабль в этом месте карты».

**— Как работает валидация? Что она ловит?**
Функция `Validate(level)` возвращает список предупреждений (не запретов —
полигон для экспериментов): центры ближе 260, пересечение поверхностей, жар
ближе 550 к спавну, жар задевает планету, спавн внутри планеты, стартовая
«планета» — звезда, радиусы вне норм (планеты 15–40, звёзды 46–64). Список
обновляется при каждом изменении.
📁 `LevelEditorWindow.cs` → `Validate`.

**— Как редактор связан с игрой?**
Оба читают/пишут ОДНИ данные — LevelAsset. Редактор пишет, WorldBuilder строит.
Никакого экспорта/импорта: изменил в редакторе → запустил Play → играешь
в изменённый уровень.

### 20.8 Инструменты и процесс

**— Откуда взялись спрайты, если графика — заглушки?**
Генерируются кодом: `StubSprites` рисует текстуры попиксельно (круг с обводкой
и мягким краем, треугольник корабля, капсула-чёрточка по маскирующей функции) и
кэширует. Editor-скрипт `StubSpriteBaker` умеет запекать их в PNG, которые
лежат в префабах. Итог: ноль внешних ассетов, вменяемый вид, замена на арт
позже — просто другой спрайт в префабе.
📁 `StubSprites.cs` → `CreateCircleTexture`, `InTriangle`.

**— Как собирались билды?**
Через стандартный Build Settings (2 сцены: MainMenu, GameScene) — есть
`SpaceTaxi-proto-v0.0.1.app` (macOS) и `SpaceTaxi-alpha-windows-v0.0.2` (Windows)
в корне репозитория.

**— Как велась разработка? Кто писал код?**
Разработка в связке с ИИ-агентом (Claude/ZCode) по ролям: программист, UI,
саунд, левел-дизайн — каждая роль работала по брифам из документов GameInfo,
агент проверял компиляцию через Unity CLI, автор запускал и тестировал геймплей
сам и принимал решения по ощущениям (пример: «камеру в 3 раза ближе», «гравитацию
×2», «стрейф слабый, давай 130»). Все решения и их даты зафиксированы в доке
проекта — история читается по документам и git-коммитам.

**— Почему константы именно такие (95, 38, 330...)?**
Они унаследованы из HTML-прототипа, где подбирались руками по ощущениям
управляемости. В Unity перенесены 1:1 (1 юнит = 1 пиксель прототипа), а затем
точечно скорректированы плейтестами: гравитация ×2, стрейф 130 вместо 85,
доворот носа мягче (8→4). Каждое отклонение — осознанное, с комментарием в коде.
📁 `PhysicsConfig.cs` — у каждого поля комментарий с прототипным значением.
